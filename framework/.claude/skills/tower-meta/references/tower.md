## 形态

```
塔 = 一个板块 = 一个常驻云会话
  作用一:和用户讨论(本板块所有话题在这一个会话里并行)
  作用二:派发任务 + 监控状态

任务 = 一个短命会话(不是 subagent)
  三条理由:① 用户能直接进去聊 ② 任务上下文不占塔的 ③ 状态可监控
```

- **一个板块一个塔,多个讨论在同一个塔里并行。** 不是一个话题开一个塔。
- **讨论住塔里(长命),任务是短命消耗品。**
- **讨论转塔**:某个讨论不再属于本板块 → 转到对应的塔。讨论跟着板块走。
- **不立总中控。** 各塔 + 文件总线够看全局。

| ops | `tower-ops` | 我们自己产品的部署、备份、监控、状态页、租户开通、切换 | 第一个里程碑前 |
| biz | `tower-biz` | 市场与销售、客户成功、合同计费、公司事务 | 一开始 |

**不在任何一个塔的范围内** —— 那是客户的事,在客户自己的项目里做。

## 谁来开塔:巡检塔是根

- **塔要由不会被重开的会话来开。** 侧栏按 `parent_session_id` 把会话挂在调用 `create_session` 的那个会话下面
  [实测✅ 2026-10,装了框架的项目实测];父会话一归档,它开的塔在侧栏跟着折叠,用户找不到 [推断]。
  归档父会话不连带子会话 —— 子会话照跑 [实测✅ 2026-10,装了框架的项目实测],丢的是侧栏里的位置。
  meta 和别的塔每月都可能被重开(见「每月深度重开」),它们开的塔迟早跟着折叠;**巡检塔不被重开,所以由它开塔** ——
  每月重开由它做,平时要代开塔(`create_session`)也找它。用户在侧栏自己开的塔是顶层会话,不受影响。
- **巡检塔由用户在侧栏亲手开**(顶层会话,不挂在任何会话下面),起名「<项目>/patrol」,开塔口令用上面巡检塔那行。
  它第一轮:活表塔表 patrol 那行填上自己的会话 ID,`ledger-push`;给自己补 `tower`、`patrol` 两个标
  (`set_session_tags`;给自己打标 [未实测])—— 每日归档靠 `tower` 标认塔。
- **巡检塔不进每月深度重开,永远不归档。** 要全新,让用户在它的窗口里手动 `/clear`(远程发 `/clear` 不生效,见〈平台事实〉)。
- **万一巡检塔的会话没了**(被误归档、侧栏里找不到了):用户在侧栏照上一条开一个新的。新巡检塔第一轮:
  1. 活表 patrol 那行写的是旧 ID —— 记下它,换成自己的 ID,`ledger-push`;
  2. `list_triggers`(带 `include_completed: true`)挑 `persistent_session_id` = 旧 ID 的,照「每月深度重开」第 7 步处理 ——
     每日、每月两条定时例程照原样(cron / prompt)在自己身上重建,再删旧的;
  3. 报给用户:改绑了哪几条。
- **代数不往下叠** [推断]:用户在侧栏开的会话是第 0 代,巡检塔开的塔第 1 代,塔派的工人第 2 代,每月重开之后还是这样。
  上限是 8(`get_session` 不带 ID 查自己,回 `lineage` 的 `depth` / `limit`)[实测✅ 2026-10,装了框架的项目实测];到了上限会怎样 [未实测]。

*出处:装了框架的项目原来是巡检塔重开 meta、meta 再重开巡检塔,两边每月互开。由会被重开的塔开出来的会话,
父会话一归档就在侧栏里找不到了,用户以为它没了;代数也每月往下多两代,照那个速度几个月就碰上限。
改成巡检塔当根、只由它开塔,两件都没了。*

## 塔的开局动作(每次唤醒)

1. 读本板块 `SKILL.md`。
2. **先同步,而且要 merge 不能只 fetch:**

   ```
   git fetch origin main && git merge --no-edit origin/main
   ```

   **只 `fetch` 不够。** fetch 只更新远端引用;**`CLAUDE.md`、`.claude/skills/`、`scripts/` 都是从
   工作树加载的** —— 不 merge 进自己分支,新规矩、新 skill、新脚本一样都读不到。
   *出处:2026-09-10,meta 塔把派发配方合进 `main` 后,其余塔谁都看不到,
   用户只能挨个去粘一句「先 merge」—— **把用户变成了传话筒**。所以 merge 写进开局第二步。*

   > **★ 传话不是问题,传空气才是。** 文件总线是**拉模型** —— 写在 `main` 上的话,
   > 对方**下次醒来 fetch 才看到**;对方不醒就永远看不到。
   >
   > **但「塔之间沟通不了」是错的,已推翻** —— 见下面〈平台事实〉里的定向唤醒条目。
   > 留言板一直都在,缺的是门铃;门铃现在有了。
   >
   > **真正的规矩是:harness 写完立刻合进 `main`,再说「各塔 merge 一下」。**
   > 顺序反了,传的就是空气。
   > *出处:2026-09-10,派发配方写完还躺在自己分支上,就让用户去叫各塔来拉 —— 拉到的是旧的。
   > 用户的意思很直白:你不合进 main,我去告诉塔有什么用。*
   > **已上闸门8**(`guard-stop.mjs`):改过 harness 却没进 `origin/main` 就在收尾时拦一次。
3. **先认时刻。** 看本轮 `now.mjs` 注入的「本轮真实时刻」,把它跟转录里工具输出的
   新鲜度分开算 —— 转录里的工具输出**不带时间戳**,而 system 块在恢复时按「现在」重渲染,
   同一屏新旧混排,分不出来就会报一份全过期的状态。
   **算「多久之前」只认机器时间戳**:git 提交时间、文件 mtime。
4. 扫 `docs/BACKLOG.md` 本板块相关条目 + `docs/journal.md` 近几行 —— **读 `origin/main` 上的**,不是自己分支的(台账走 main,见 CLAUDE.md)。
5. 两三行状态汇报 → 待命。**不主动开工。**

## 六条协议

1. **落盘即关**:任务闭环 → journal 一行 → 关掉或沉底。
2. **开局声明宽松化**:板块必报;任务可以是「先看」,看完再定名。
3. **派发**:首次派活的**全文直接塞进新会话的开场白**,含路径与验收标准,
   **冷启动可接手** —— 跨会话补话很贵。
4. **跨板块流转:`docs/BACKLOG.md` 收件箱一行是权威记录。** 要对方动手的,写完**同一轮按门铃**
   (先 `ledger-push`,再 `create_trigger` 绑对方塔当前会话 → `fire_trigger`),闸门14 收尾时核;只抄送的塔写进括号(`→ ops(抄 plan)`),不算要它动手。
   不用对方动手的(只是告知),回复里单独一行写「不按门铃:理由」放行。**门铃不替代留言板** —— 门铃只说去读哪一行,话在台账里。
   闸门14 只认收件箱模板那种行格式(`- YYYY-MM-DD HH:MM · <源> → **<目标>** · …`);收件箱写成每塔一个标题、条目写在标题下的项目,
   要对方动手的那条照这个格式补一行,不然闸门14 看不见它。
5. **状态两层**:状态层 = journal + BACKLOG;内容层 = 平台转录。
   **塔答「现在什么状态」永远先查文件总线,不凭记忆。**
6. **任务会话里冒出塔话题**:一句话答完 + 收件箱记一行,深聊移步塔。

### 会话工具断了:自己当闹钟重试

会话工具(`create_session` · `send_later` · `create_trigger` / `fire_trigger` · `get_session`)报「does not offer this tool here」之类不可用时,
**`send_later` 自己也在断的那批里,排不了回查** —— 别停在那儿等人来叫。
1. 用 Bash 后台(`run_in_background`)跑 `sleep 600` 当闹钟 —— 不靠会话工具;后台命令一结束,会话被叫醒开新一轮,醒来再试那个工具。
2. 最多 6 次(约 1 小时)。回来了就接着干;6 次都不行 → 台账写一行「卡在哪 · 要什么」(会话工具断了、手上要派的活),停,等用户或下一次门铃。
3. 断之前手上已经排着的回查别删 —— 它到点照样叫醒你(装了框架的项目实测:断了之后靠事先排的回查接上,只停了二十几分钟)。

[未实测] 后台闹钟叫醒的那一轮工具会不会回来 —— 实测那次是别的塔按门铃开的新一轮让工具回来的;下次真断时把结果记到这里。
*出处:装了框架的项目里,一个塔夜里会话工具全断,用掉了最后一个回查、排不了下一个,停了 11 个小时,
直到别的塔按门铃才接上 [实测✅ 2026-10]。*

## 平台事实

- **本机会话的 `list_sessions` 看不到云会话**(2026-09-09 本机实测)。
  云塔之间**能**互列、而且能同时列到云端和本机会话(2026-09-09 云塔实测)。
  **推论**:本机看不见云端,云端两边都看得见 —— 但跨会话的权威流转仍然走文件总线。
- **★ 定时例程(cron)有两种绑法,差别很大(2026-09-15 实测)。**

  | 绑法 | `create_trigger` 怎么传 | 开出来的会话身上有什么 |
  |---|---|---|
  | **开新会话** | `create_new_session_on_fire: true` | **没有仓库** —— `session_context` 里没有 `sources`,而 `create_trigger` **也没有传仓库的参数**(`source_url` 只有 `create_session` 有)。所以它 `git fetch` 不了、读不到台账、跑不了 `ledger-push` [实测✅] |
  | **绑到已有的塔** | `persistent_session_id: <塔的会话ID>` | 塔的一切 —— 仓库、工作树、MCP 工具、skill。**要动仓库或台账的例程只能走这条** |

  *出处:2026-09-15 建「每日清理工人会话」例程,第一版用开新会话模式,
  明确要它「不管有没有东西归档都往 journal 写一行」—— **它一个字都写不出来**,
  因为身上没仓库。改成绑 meta 塔才成。现在每日、每月两条例程都绑在巡检塔上(见「谁来开塔:巡检塔是根」)。*

  > **⚠ 删这种例程会把它开出来的会话一起带走。** 试跑那个会话在触发器删掉之后
  > `get_session` 返回 `not found`、`list_sessions` 里也没了 [实测✅ 2026-09-15]。
  > **要读它的摘要或产出,必须在删触发器之前读。** 当时就是这么把一条待验的事实弄丢的。
  >
  > **仍 [未实测]**:开新会话模式到底有没有 `mcp__*` 工具。建触发器时平台会警告
  > 「stores no MCP connectors」;绑已有会话时**不成立**(2026-09-10 两个塔醒来都用了 GitHub 工具),
  > 开新会话的没验出来 —— 想验就再建一个、**先读摘要再删**。
  >
  > 另注:那次试跑用的模型**不是会话配置的那个**(是个更小的模型)。例程开出来的会话用什么模型,别想当然。

- **★ 定向唤醒能用 —— 塔之间真能互相叫醒(2026-09-10 实测✅,推翻 2026-09-09 的结论)。**
  `create_trigger`(带 `persistent_session_id`,不给 cron 也不给 `run_once_at`)→ `fire_trigger`,
  一句话直接投进另一个塔的会话。**实测两塔两分钟内全部醒来并干完活**:

  | 相对时刻 | 事件 |
  |---|---|
  | +0:00 | meta `fire_trigger` → 塔 A |
  | +0:31 | meta `fire_trigger` → 塔 B |
  | **+2:17** | 塔 B 核完、经 GitHub 合了自己板块的 PR(合并提交带 `(#<PR 号>)` 后缀可证) |
  | +3:04 | 塔 B 台账推 `main`:收掉那一单、删队列行 |
  | **+3:29** | 塔 A 核完、合了自己板块的 PR |
  | +6:14 | 塔 A 台账推 `main`:收单 |

  **2026-09-09 那次测出「发得出但消息丢了」,2026-09-10 复测是通的** —— 原因不明(平台变了,还是那次测法有问题),
  两个日期都记着,别再把旧结论当既成事实。

  > **⚠ 一条警告没应验,但别当它不存在。** 建触发器时返回
  > 「this trigger stores no MCP connectors, so the sessions it fires will run without
  > connector tools」。**绑到已有会话(`persistent_session_id`)时不成立** ——
  > 两个塔醒来都用了 `mcp__github__*` 合 PR [实测✅ 2026-09-10]。
  > 但**新开会话的触发器会不会掉工具,没验** [未实测]。

- **peer messaging(`SendMessage` / `ListAgents`)仍然够不到别的云塔**(2026-09-09 实测,
  2026-09-10 复验 `ListAgents` 仍返回空,**2026-09-24 两个方向都复验 ❌**):每个云塔是独立容器,只看得见自己容器里的。
  **要叫醒别的塔走上面那条定向唤醒,不是走 `SendMessage`。**

  > **2026-09-24 那次怎么测的**(验证平台那句「cloud session 收得到你的消息,但还不能回消息给任何会话」过没过时):
  > 开一个不挂仓库的一次性探测云会话 `<探测会话名>`,让它 `SendMessage` 给 meta 塔 `<meta 会话名>`
  > → **`agent not found`**;反过来 meta 发给 `<探测会话名>` → **`No agent named '<探测会话名>' is reachable`**。
  > **平台那句没过时,而且实际比它说的还窄**:不止「不能回」,云 ↔ 云连「发过去」都不通。
  > 迷惑人的地方:`ListAgents` 会告诉你「本会话叫 `<会话名>`,这是别的会话给你发消息用的名字」,
  > `SendMessage` 的说明也写着名字能解析到云端 —— **文字写着能,实测不能**。铁律3 的标准样本。

- **三条通道,分工别混**:

  | 通道 | 怎么走 | 延迟 | 干什么用 |
  |---|---|---|---|
  | **文件总线** | 写 `main` 台账,对方下次醒来 fetch | 对方不醒 → 永不到 | 沉淀、留痕、谁都能读 |
  | **定向唤醒** | `create_trigger` + `fire_trigger` | 秒级 [实测✅] | 点对点、有时效的一句话。**塔 ↔ 塔、塔 → 工人都通** |
  | ~~`SendMessage`~~ | peer messaging | — | **云 ↔ 云两个方向都 `not found`** [实测❌ 2026-09-24],别用 |
  | **GitHub 事件** | `subscribe_pr_activity` | 事件驱动 | 「PR 好了」「CI 红了」[未实测] |

  **门铃不替代留言板。** 唤醒只响一次、不留痕;台账才是账。
  叫醒之后该记的还得记进 `journal.md` / `BACKLOG.md`。

  **★ 反过来也成立:只写留言板不按门铃 = 对方不知道。** 2026-09-24 一个塔夜里给另一个塔提了两个问题,
  只写了收件箱没按门铃,对方没被叫醒,**用户问了才看到,晚了约 7 小时**。所以塔之间的规矩是**两样都做**:
  先把话写进台账(留痕、给转授权当出处),再 `fire_trigger` 叫对方去读。
  *(一次犯,先记文字规矩;再犯就上闸门 —— 装了框架的项目又犯了两次,所以上了**闸门14**:往收件箱写了要对方动手的留言、
  之后没按对应塔的门铃,收尾时拦一次;只是告知的,回复里单独一行写「不按门铃:理由」放行。)*

  **按门铃的两条平台脾气,各有一道闸**(细节见本框架的 `docs/platform-facts.md` §1.1):
  同一个门铃只按一次 —— 按第二次话不进目标会话,平台另开一个空会话(**闸门16** 按之前拦一次);
  按完核回执 —— `cse_<Y>` 去掉前缀跟目标 `session_<X>` 去掉前缀相等才算送到(**闸门15** 收尾时核)。
  塔断开了照按新门铃,叫得醒,不用等用户;已断开的工人叫不醒。

- **★ 塔 → 工人的定向唤醒也通(2026-09-24 实测✅)。** 工人开工时规格还是旧版,
  几分钟后规格改了新版;验收塔 `create_trigger(persistent_session_id = 工人会话)` → `fire_trigger`,
  **工人收到并照做**(改按新规格验)。推翻了更早那条「塔够不着自己派出去的工人,任务书一旦发出就改不了」
  —— 那条说的是 `ListAgents` / `SendMessage` 够不着,**定向唤醒够得着**。
  用法仍要克制:工人短命,**只在任务前提变了的时候叫**(规格改了、要验的对象换了),别拿来催进度。
- **claude.ai 一次只能连一个 GitHub 账号**,多账号是未实现的功能请求。
  **★ 切账号会让本仓库全部塔同时断 git**(2026-09-24 实测):用户为另一个项目把连接切到别的账号后,
  约十分钟里各塔 `git fetch` 报 `repository not found`、`git push` 报 `could not read Username`,
  `mcp__github__*` 报 `invalid session`。**所有塔一起断**,正在跑的塔也推不了。
- ~~协作者身份不算~~ **协作者身份算,至少对 git 算**(2026-09-24 实测✅,推翻旧条):
  用户连上另一个账号、把它加成本仓库的 Collaborator 之后,`git fetch` / `git push` 立刻恢复。
  **所以一个账号当两个仓库的协作者,就能同时服务两个项目** —— 不用来回切。
  **但 `mcp__github__*` 在已经在跑的会话里没跟着恢复**:git 通了之后仍报 `invalid session`
  (建 PR / 合 PR 都走它,所以还是卡)。**会恢复,但要换连接**:塔被叫醒后 MCP 就通了,
  而它断之前派出去、还在跑的工人仍是 `invalid session` [实测✅ 2026-09-24]。
- **远程发 `/clear` 不生效**(2026-09-24 实测❌):用定向唤醒往会话里投一条 `/clear`,平台把它当普通消息收下 ——
  探测会话照样记得清之前给它的口令,上下文还涨了(79,775 → 81,852)。**斜杠命令只认人在输入框里敲的。**
  所以「给塔清肚子」自动化不了;能自动的是平台的**自动压缩**,见下一条。
- **★ 自动压缩的触发点能在仓库里调:`.claude/settings.json` 写 `"autoCompactWindow": <数字>`**(2026-09-24 实测✅)。
  探测会话检出带 `150000` 的提交:平台报 `max_tokens: 150000`(平时是 1,000,000),一轮里读台账撑上下文,
  **自动压缩了 2 次**,收在 10.3 万。**必须写数字** —— 写字符串 `"150k"` 被静默忽略
  (`max_tokens` 仍是 100 万,涨到 26 万也不压)[实测❌]。二进制里读这个值用的是 `Number(...)`。
  默认 `auto` 对 100 万窗口的模型基本不压 —— 所以塔会胖到三五十万。**不热加载**:
  已在跑的会话工作树里带着它将近一分钟,没被热加载、没压缩;把含它的 `main` 并进工作树,那一轮也没变 [实测✅ 2026-09-25]。
  **但老会话不用重开也会切过去**(2026-09-25 实测✅):一个设置生效前开的老塔,一次自动压缩时
  `preTokens: 784933`(还在按 100 万压);随后被回查叫醒(恢复),两分钟后又自动压缩,这回 `preTokens: 240213`
  (已经按 30 万压了),`get_session` 报 `max_tokens: 300000`。两次之间只发生过「一次压缩 + 一次恢复」——
  **是哪一个让它重读的,分不开** [未实测]。分辨法:找一个设置生效前开的、上下文不到窗口 80% 的塔按一次门铃
  (只恢复、不会压缩),看它的 `max_tokens`。**不管是哪个,对塔的影响一样**:老塔再被叫醒或压缩一次,就切到新窗口了;
  这时上下文已经超过新窗口约 80% 的,下一次调用会先自动压缩(实测那次压了约 100 秒才开始干活)。
  **框架默认 `300000`**。默认有多晚?实测转录里记着一次自动压缩
  `preTokens: 788922 → postTokens: 12507` —— **平台默认要到将近 79 万才压**,所以不设的话塔一直胖到五六十万。
  闸门9 v3 从这个设置**现读**窗口(只认数字,跟平台一样),在 70% 提醒落盘,**每压缩一次重新提醒一次**。
  还没切到新窗口的老会话,闸门9 会比平台压缩早报 —— 过渡期的事,不修。
  压缩后开局 hook 从会话 ID 重新认出「你是 X 塔」,身份丢不了。
- **`get_session` 里的 `context_usage` 不是实时的**(2026-09-25 实测✅):开工 13 分钟、正在跑的工人,
  `used_tokens` 还是 `0`;一个会话已经压到 12,582,2.5 分钟后读到的还是压缩前的 `778288`;
  下一次压到 19,524 之后读到的是 `232195`。**只当「它上一次上报时」的数**,别拿来判断一个塔现在多胖。
  准数在会话自己的转录里:每次压缩记一条 `compact_boundary`,带 `preTokens` / `postTokens` —— 只有本会话读得到自己的。
- 云塔醒来是陈旧克隆,**开局第一件事 `git fetch`**。
- **往已归档的会话按门铃,当场报错**(2026-09-25 实测✅):`create_trigger` 绑已归档会话 →
  `Session … is archived; only active sessions can be bound to triggers`。**不会悄悄丢消息**,但塔重开过
  (见「每月深度重开」)之后,按门铃前要先去 `origin/main` 的活表(`docs/session-pool.md`)查对方**当前**会话 ID。
  闸门14 也照活表塔表那一格(第一个 `session_…`)核门铃按没按对塔 —— 塔重开了活表没换 ID,它就会拦。

## 每月深度重开

**第一层**是自动压缩(`.claude/settings.json` 的 `autoCompactWindow`,框架默认 `300000`),天天自己跑。**第二层**是这一节:每月 1 号一次
(默认凌晨 04:23,按 `.claude/belltower.json` 的 `timezone`;cron 写 `CRON_TZ=<你的时区> 23 4 1 * *`),绑在**巡检塔**上的例程照这一节,
对每个塔做「收尾 → 归档 → 重开」,清掉压缩摘要里慢慢攒的偏差(「某个塔压缩几次之后忘了自己是塔」就是这种偏差)。
**例程只写「照 tower.md 这一节做」,步骤只在这里改** —— 规矩只存一份。
*装了框架的项目起初每周一轮,跑过一轮全量(五个塔约 $23)后改成每月。*

**谁会被重开**(四条全中才动):
1. 活表塔表里有会话 ID 的塔,**只除外巡检塔**(例程绑在它身上;它是开塔的根,不重开 —— 见「谁来开塔:巡检塔是根」)。
   **meta 纳入**,跟别的塔同样四条判据、同样八步。
   *例程原来绑在 meta 上时 meta 除外;改绑到巡检塔之后,这条理由没了。*
2. **开局之后动过**:`updated_at` 减 `created_at` 不到 15 分钟 = 开完局就没再动过,没攒偏差,重开白花钱。
   *装了框架的项目第一次全量跑,有个塔上一次开局 34 秒后就没再动过,就是按这条跳过的。*
3. **开局满三周**(`created_at` 在 21 天前)—— 刚开的塔(上一轮开的、用户手动重开的)偏差还没攒起来。
   *为什么要这条:1 号是死日子,跟塔上次开局隔多久没关系。装了框架的项目改成每月后的第一个 1 号,几个塔几天前刚开过,全按这条跳过。*
4. **现在闲着**:塔不是 `RUNNING`;它派的工人(`parent_session_id` = 它)没有 `RUNNING` 的;6 小时内没动过
   (用户可能刚跟它聊完)。**有一条不满足就跳过,报给用户。**

**步骤**:
1. **收尾 —— 按门铃**:`create_trigger`(`persistent_session_id: <会话ID>`,绑那个塔)+ `fire_trigger`,内容照抄:
   「【每月深度重开 · 收尾】把进行中的讨论、等用户答的问题、排着的回查(send_later)、在跑 / 待收的工人
   写进台账(journal 一行 + 该进 BACKLOG 的进 BACKLOG);该推的推、该合的合。最后一行只写 `HANDOFF-READY`。」
2. 排一个 20 分钟回查(`send_later`,打回**巡检塔**)。回查时逐个 `get_session`:`IDLE` 且摘要 / 最后一行有
   `HANDOFF-READY` → 往下;没有 → **这个月跳过**,报给用户。
3. **归档旧会话** `archive_session` —— **不删除**,转录要能回查(铁律「不认自述、要能回查」)。
4. **开新会话** `create_session`(巡检塔调,新塔挂在它下面):
   - `source_url` 本仓库、`source_revision: main`(**两个都传**;漏了 revision,新塔在侧栏落进「Other」,闸门13 会拦一次);
   - `title` **照搬旧会话的标题**(用户在侧栏按「项目/板块」起的名,如 `Proj/dev`;别换成光秃秃的塔名);
   - `tags: ["tower", <塔名>]`(**不带 `worker`**,每日归档靠 `tower` 标认塔;
     旧会话上的 `config:*` 标签是平台给开了 MCP 的会话自动加的,不用照搬);
   - `model` **用例程 prompt 里写的那个** —— **模型名只写在例程里,不进仓库**。例程没写才照搬旧会话的 `session_context.model`
     (旧塔的 `configured_model` 是建会话时的默认,别照那个抄);两样都不传就继承巡检塔自己的模型;
   - `prompt` **只写 `/effort max`** 一行。开会话的第一句是斜杠命令,平台当命令执行、不跑模型
     [实测✅ 2026-09-29,装了框架的项目实测:开出来 10 秒就 `IDLE`,`session_context.effort_level` = `max`,没有 `usage`、没花钱]。
     `create_session` 本身**没有** effort 参数;项目 `settings.json` 的 `effortLevel` 按文档不收 `max`,而且会连工人一起改 —— 所以走这条。
5. **按门铃送开塔口令**:等新会话 `IDLE`、`get_session` 看到 `effort_level: max`,再 `create_trigger`(绑新会话)+
   `fire_trigger`,内容 = 开塔口令一行 + 「上一任的接手须知在 journal 里本塔最新一条」。
   **档位只能在第 4 步设**:门铃送进去的 `/effort` 不当命令 [实测✅ 2026-09-29,装了框架的项目实测:按门铃发 `/effort high`,
   档位还是 `max`,模型把它当普通消息跑了一轮]。这个开局门铃下个月按第 7 步当「按过的门铃」删。
6. **更新活表**:塔表那一行换成新会话 ID,`ledger-push`。这一步之前新塔开局 hook 认不出自己,
   但开塔口令里写了板块,不影响;之后每次被叫醒都认得出。
7. **处理绑在旧会话上的例程**:`list_triggers` 要带 **`include_completed: true`** 全翻 —— 不带的话跑完的一次性回查不列
   (实测一次默认看到 4 个,带上才是 8 个)。例程表攒多了几百条、一页十几万字符,超工具输出上限:落盘再用脚本读,
   条目在键 `data` 下,翻页看 `has_more` / `next_cursor`。挑 `persistent_session_id` = 旧 ID 的,分四种:
   - **定时例程**(有 cron)→ 照原样(cron / prompt)绑到新 ID 重建,再删旧的 —— 绑在已归档会话上的例程会失效;
   - **还没响的一次性回查**(`run_once_at` 在将来)→ 跟定时例程一样搬 [未实测:推论,实测那次没碰上];
   - **按过的门铃**(没有 cron、没有 `run_once_at`)→ **直接删,不重建** —— 门铃一次一个,下回要叫对方另建;
   - **响过的一次性回查** → 平台已自动停用,不用管。

   一次要删的门铃会很多(装了框架的项目一轮五个塔删了八十多个):**删门铃交给一个子代理**,给它 ID 清单文件、
   只许删清单里的、回报删了几个 / 哪个报错 —— 塔的上下文里别铺几十次删除的回显。
   有的删除会被 auto 模式的权限分类器拒(判成不可逆删除):别重试、别绕,ID 记进台账报用户 [实测✅ 2026-10,装了框架的项目实测]。
   删绑在已有会话上的例程,不连带删那个会话 [实测✅ 2026-11,装了框架的项目实测]。
8. **报给用户一张表**:谁重开了(侧边栏新会话的名字、`get_session` 现查的模型和档位)、谁跳过了(为什么)、花了多少、
   **每个新塔第几代**(`lineage.depth` / `limit`)。巡检塔是第 0 代,它开的新塔都该是第 1 代 —— **不是 1 就单独标出来**
   (开它的不是顶层的巡检塔,查一下);**到 6 单独提醒用户**(塔第 6 代,它的工人第 7 代,上限 8;到了上限会怎样 [未实测])。
   代数怎么拿:巡检塔 `get_session`(不带 ID)查自己能读到自己的 `lineage`,新塔 = 它 + 1;
   查别的会话没回 `lineage` [实测✅ 2026-11,装了框架的项目实测]。

**代价**(每个塔):收尾一轮(按当时上下文)+ 新会话开局一次
[实测 2026-09,装了框架的项目:首次全量五个塔 —— 收尾 $1.4–6.8(还在 100 万窗口、上下文四五十万的两个最贵),
开局 32–74 秒、$0.6–0.9,开局就占上下文 11–12 万;一轮合计约 $23]。一月一次,比塔胖到几十万上下文、每轮都按大上下文计费便宜得多。

**会丢的,重开前心里有数**:会话 ID(按门铃前查活表)· 用户在侧边栏跟旧塔的聊天窗口(变只读,内容都在)·
用户在侧栏单独给某个塔切的、跟第 4 步不一样的档位(别的 effort、别的开关)—— 新塔一律 `max`,要别的让用户在侧栏再切。
`create_session` 没有 effort 参数;`max` 是第 4 步 prompt 只写 `/effort max` 设上的。

**还没验的**:第 4 步设的 `max` 在容器被回收、下次唤醒重启之后还在不在 [未实测]。它落在服务端的
`session_context.effort_level`,跟用户在侧栏设的是同一个字段(装了框架的项目里,侧栏设成 `max` 的塔隔夜换过容器醒来还是 `max`),
[推断] 会留。下次真跑重开后,等新塔第一次隔夜再醒,`get_session` 看 `external_metadata.effort_level`(容器自己报的)。

## 云环境配置

| 字段 | 填什么 | 理由 |
|---|---|---|
| Environment variables | **空**(最多 `GIT_AUTHOR_NAME` / `GIT_AUTHOR_EMAIL`) | 对话框自己写明「对所有用此环境的人可见,别放密钥」 |
| Setup script | 还没代码时**空**;有代码后填装依赖的命令 | 没代码就没什么可装 |
| Network access | Trusted | 塔要连 github.com 做 fetch / push |
