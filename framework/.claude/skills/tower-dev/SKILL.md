# 开发板块(tower-dev)

> 这是框架给的**起步模板**:起步时拷进项目一次,之后归项目自己改。
> 带 `<!-- 项目填写:… -->` 的地方请换成本项目的内容。

## 边界

**dev 建东西,不定东西。** 做什么、算不算做完归 `tower-product`;日期工时归 `tower-plan`;
验收归 `tower-test`(dev 自己的测试绿 ≠ 验收过);测试素材归 `tower-data`;线上运行归 `tower-ops`
(ops 开塔之前 dev 兼)。

**没有规格不开工。** 规格在 `docs/product/specs/`,验收标准在 `docs/product/acceptance.md`。
**开工前先确认设计过了评审** —— 而且「过了」要能在台账里找到**用户的原话**,不是某个塔自己写的「解除阻塞」
(见 `tower-plan`〈评审与解除阻塞〉)。别拿着待评审的图开始建表 —— 数据模型事后改极贵。

## 现状

**代码现状不写在这里** —— 开局 `session-start.mjs` 每次现数(代码目录由配置项 `codeDirs` 决定,默认 `src`)。
*出处:文档里手写的「零代码」在主干已经有几十个文件之后还挂着,每个塔开局都读那句当真。
状态被存下来了,没人保证它跟事实同步 —— 派生优于存储。*

## 测试与证据

**说「完成」前贴证据**(CLAUDE.md 铁律4)。建库时第一件事就是把测试体系立起来:
单元测试 + 迁移测试 + 接口契约测试,**一条命令跑完,退出 0 才算过**,CI 跑同一条。

- 交活时贴的是**今天真能跑出那个结果的命令 + 输出**,不是「测试全绿」四个字。
- 本机 / 云容器能跑的起服务步骤写进 README 或脚本,test 塔要照着起。
  **README 和 Makefile 说法不一致时,以实测为准并改掉错的那个。**
- PR 合进 `main` 要走 CI;分支保护开着就开 PR + auto-merge。

## 取测试数据要先问

要用真实数据做验证素材,**必须先拿到用户确认**(CLAUDE.md 铁律1,敏感数据默认不进库)。
取哪一份、脱敏到什么程度、进不进版本库,逐次问。归 `tower-data` 统筹,dev 不自己去取。

## 派工与号段

dev 塔讨论、拆活、收活;**成品活派工人做**(配方见 `.claude/skills/tower-meta/references/dispatch.md`)。
号段默认 `Q3xx`(`.claude/belltower.json` 的 `ranges` 可改;开局认出塔身份时会打出来)。立号前要有用户那句「做这个」落在台账上(铁律6)。
**收活自己查 PR 和 CI,不认工人自述**(铁律7)。
