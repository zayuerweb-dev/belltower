## 这个板块管什么

**我们拿真实数据来验证我们的产品。** 方向要搞清楚:不是替数据的主人干他们的日常,
是把真实数据当成**测试素材**,用来证明产品的核心逻辑(抽取、判定、计算……)是对的。

## ★ 取数铁规矩(CLAUDE.md 铁律1)

**敏感数据默认不进本仓库。每要用一份,先问用户。** 这是**确认闸,不是禁令** —— 真实数据迟早要用,
规矩是**不许自动流进来**。三件事逐次确认:

1. **取哪一份** —— 具体到批次、到文件,不要「把那个目录拷过来」。
2. **脱敏到什么程度** —— 公司名、人名、地址、邮箱、单号,哪些要替换成占位符。
3. **进不进版本库** —— 大概率不进;进的话要用户明确说进。

`.gitignore` 里那串硬排除是这条规矩的默认值(闸门另有 `sensitivePaths` 配置兜底)。
要放行某一份,**先拿到确认再改规则**,不要反过来。

*教训:整个外部目录被 `git init` 后原样推进仓库,里面九成是别人的数据,含法定全称、办公地址、邮箱域名 ——
没人问过就上了远端,只能用干净历史重建仓库。所以要进仓库的数据,每一份都要有一次确认。*

## 验证素材该长什么样

**理想形态:脱敏后的 fixture,不是原始文件。**

| 层 | 素材 | 说明 |
|---|---|---|
| 单元 | 内联表格 | 纯函数,不需要真实数据 |
| 管线重放 | 脱敏样本 + 模型输出缓存 + expected.json | **零 API 费用**,每次改动都能跑 |
| 端到端 | 少量真实样本 | 慢,发版前跑 |
| 批次对照 | 整批自动结果 vs 人工修正结果 | 有新批次时跑,用来**发现**新错误 |

**能复现的错必须做成 fixture,做不成 fixture 的错等于没修**,下次还会来。

## gold set 的价值

规则的质量只能靠对照真值来测。人工逐条确认过的修正记录,是产品最难复制的资产之一 ——
但它是**数据主人的**,不是我们的。我们能带走的是**从中学到的规则**,不是数据本身。这条边界要一直守着。

## 换模型 / 改 prompt 必须跑回归

任何换模型、改 prompt、改规则的动作,**跑一遍 gold set 再说结论**。
「感觉更准了」不是结论(CLAUDE.md 铁律4)。

## 成本实测

模型调用的单价、每条样本的 token 量、每批的总成本 —— **实测一次写进 `docs/`,带命令**。
估算要标 [未实测],不当定稿依赖(铁律3)。

## 与其他板块交接

| 方向 | 载体 |
|---|---|
| ← product | 采集到的检查清单、导出格式、文档模板 → 整理成验证素材 |
| → dev | fixture + expected + 回归命令;dev 改动后自己跑 |
| → test | 验收用的样本数据;test 缺什么来要,**test 不自己去碰原始数据** |
| → ops | 迁移校验脚本(旧系统 → 新系统,逐条对账) |

## 号段与派工

号段默认 `Q4xx`(`.claude/belltower.json` 的 `ranges` 可改)。派工人照 `.claude/skills/tower-meta/references/dispatch.md`。
**给工人的任务书里不许夹真实数据**;要用哪份,任务书写路径 + 用户确认的原话与时刻。

## 顾问姿态

先讲清词 → 给选项和推荐 → 一次只问一个 → 每条断言带证据标 → 决定进 `docs/`。
