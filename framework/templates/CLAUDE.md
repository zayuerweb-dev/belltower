## 铁律

1. **敏感数据默认不进本仓库;每次要进,必须用户明确确认。**
   这是**确认闸,不是禁令** —— 真实数据往往是唯一的验证素材,迟早要用。规矩是:**不许自动流进来。**
   要用哪一份、脱敏到什么程度、进不进版本库,**逐次问用户**。
   `.gitignore` 里的硬排除和 `.claude/belltower.json` 的 `sensitivePaths`(bash / edit 两条正则)就是这个默认值的实现;
   要放行某一份,先拿到确认再改规则。
   *教训:把别处的一个目录整个 `git init` 推进仓库,里面绝大多数是第三方的真实资料(名称、地址、联系方式、合作名单),
   没人问过就上了远端。发现后只能用干净历史重建仓库。所以默认挡住,逐次放行。*

   <!-- 项目填写:本项目的敏感数据具体指什么、放在哪、谁能确认(对应配置项 sensitiveReminder)。 -->

2. **别伸手去动别的项目的目录。** 相邻的项目有它自己的 git 仓库和 harness。
   要改它就去那边开会话,不要从这里伸手。

   <!-- 项目填写:有哪些相邻项目、它们在哪(写成相对说明,别写本机绝对路径)。 -->

3. **未实测的不得当定稿依赖。** 「平台能不能做 X」这类断言,当场研究加实测再定;
   测不了的显式标 **[未实测]**,别当既成事实。
   *教训:协议从别的项目搬来,那边实测过、这边没有;混为一谈会拿着错的前提做决定。
   平台文档写着「能」、实测「不能」的例子见 `docs/platform-facts.md`。*

4. **说「完成」前贴证据。** 可测量的断言要么附一条今天真能跑出那个数的命令,要么删掉。
   没有输出就不是完成,是「我以为」。

5. **报号必带一句话内容。** 提 `T2` / `M1` / `Q101` / 某个文档名时,必须在同一句里写清它是什么。
   只报号 = 让用户反过来问「那是什么」。
   *教训:用户被一串编号轰炸之后原话大意是「别老说 某某号 没做,我得知道它是什么」。*

6. **派活要用户点头;别的塔的活不许替它立号。**
   塔不许自己想出一件活、自己立号、自己派工人 —— **立号前必须有用户那一句「做这个」**。
   立号 / 写任务书 / 派工人 / 收活核 PR,只能是**那件活所属板块的塔**自己干。
   `.claude/hooks/guard-edit.mjs` 闸门4(台账侧)和 `guard-mcp.mjs` 闸门10(派工人那一刻)各拦一次问这两句。

   **★ 但「用户点头」不等于「用户对你本人说过」。** 用户的正常流程是:跟一个塔讨论 →
   规划出来 → 出 Q → 派。那句「做这个」发生在**讨论里**,要求他对每个塔再说一遍,
   就是把他变回传话筒 —— 正是这套框架要拆的东西。
   **判据是「那句话存不存在、查不查得到」,不是「对谁说的」:**

   | | 算数吗 |
   |---|---|
   | 用户在**别的塔**说「照这个做」,原话 + 时刻已落进台账,你读得到 | ✅ 算 —— 照着派 |
   | 你**自己想出来**一件该做的活,理由再充分 | ❌ 不算 |
   | 别的塔**转告**你「用户要做 X」,但台账上找不到那句原话 | ❌ 不算 —— 先让它把原话落盘 |

   转授权的做法见 `.claude/skills/tower-meta/references/dispatch.md` §11。
   *教训:一个塔自己挑了一件「该做的」活立号派出去,又顺手替另一个塔在队列里写了一行。
   用户的反应是「这个号是谁创建的,我说过吗」「写号发号也不是你的活吧」。
   另一面:用户说「我在一个塔规划完就出号派了,以前是我传话,现在可以直接沟通了」—— 所以原话落盘即可转授权。*

7. **用户看不见工人,塔得替他看 —— 而且别等他来问。**
   工人是另开的会话、另一个容器,用户在自己那个窗口里**一个都看不到**。
   - **派完工人,同一轮里排一个 10 分钟回查**(`send_later`,打回本塔)。到点自己醒来查、
     自己报,用户什么都不用问 [实测✅ 2026-09-10]。配方见 `dispatch.md` §10,模板见 `docs/routines.md`。
   - 被问到「现在谁在跑」时:**查 `list_sessions` + GitHub PR,不要念活表** ——
     活表是各塔自报的会过期;`IDLE` ≠ 干完;工人自述只当线索。见 `dispatch.md` §9。
   *教训:用户原话大意「塔在派工人跑,只是我看不到」「还要我问『现在谁在跑』」。*

### ★ 通用教训:塔可以给自己签字解除阻塞(闸门5 的由来)

一个条目原本写着「等用户拍板,**阻塞全部开发**」→ 负责评审的塔自己做完了评审、自己在台账写下
「有条件通过,**开发解除阻塞**」→ 另一个塔读到这行就派了工人 → 第一批代码合进了 `main`。
**全程没有用户那一句「做这个」。** 用户事后选择追认,但这条路本身是个洞:

**铁律6 拦的是「立号」,拦不住「解除阻塞」—— 判据写在台账里,而台账是塔自己写的,塔可以给自己签字。**

所以上了 **闸门5**(`guard-edit.mjs`):往台账**新增**授权词(「解除阻塞」「评审通过」「已授权」「可以开工」「用户同意」……),
而同一笔里没有「用户 + 时刻 / 原话」→ 拦一次。用户真点过头的,把原话贴上就放行。

## 板块路由

默认八个板块,对应八个塔(清单可在 `.claude/belltower.json` 的 `boards` 里配置)。
**每一个都围绕本项目的产品,不围绕任何客户的日常业务。**

| 干什么活 | 技能 | 塔 |
|---|---|---|
| 路线图、里程碑、工时与范围取舍、提案、定价策略、优先级(消化 BACKLOG) | `tower-plan` | <!-- 项目填写:现在开 / 何时开 --> |
| 用户是谁、做什么不做什么、长什么样、算不算做完:访谈、规格、线框到原型、验收标准、指标 | `tower-product` | <!-- 项目填写 --> |
| 建产品本身(数据库、接口、前端、管线);没有规格不开工 | `tower-dev` | <!-- 项目填写:通常设计评审过后开 --> |
| 测试数据与验证(真实数据取数要确认,见铁律1)、迁移校验、成本实测 | `tower-data` | <!-- 项目填写:通常随 dev 开 --> |
| **验收 dev 交的东西**:按 product 的标准自己起服务、自己点、自己跑;报缺陷带复现;守回归。不写业务代码 | `tower-test` | <!-- 项目填写 --> |
| **我们自己的产品**怎么跑在线上:部署、备份恢复、监控、状态页、密钥、租户开通、切换 | `tower-ops` | <!-- 项目填写:上线前开,之前 dev 兼 --> |
| 市场与销售、客户成功、合同与计费、公司事务 | `tower-biz` | <!-- 项目填写 --> |
| 会话机器本身(上下文 / 闸门 / 总线 / 塔 / 各塔工具箱) | `tower-meta` | 现在开 |

**`tower-ops` 管的是我们自己产品的运维,不是客户业务的运维。** 客户自己的日常操作归客户那个项目,不归这里。
`tower-data` 管的是**拿真实数据来验证我们的产品**,方向反过来的。

**各板块共用一种顾问姿态**(用户不一定懂每个职能):先讲清词 → 给选项和推荐 → 一次只问一个 → 每条断言带证据标 → 决定进 `docs/`。
详见 `docs/architecture.md`(本框架仓库里)。

**★ 说了要做的,一次做完再汇报。** 报了「我按 ①②③④⑤ 做」然后做完 ① 就回来,等于把**交付**换成了**进度播报**,
逼用户一遍遍说「要」「开」「继续」。中途只在**真被挡住**时停(要拍板、要凭据、要外部的东西),
停的时候说清**卡在哪、需要你给什么**,不要问「要不要我继续」。
*教训:列了五步、做完第一步就回来汇报,用户只能一遍遍追问 —— 同一晚这样停了不止一次。*

**门铃不替代留言板。** 塔之间可以用定向唤醒(`create_trigger` 绑对方 `persistent_session_id` + `fire_trigger`)叫醒对方,

### ★ 台账走 `main`,代码走自己分支

**总线只有一条才叫总线。** 各塔被开在各自分支上,写在自己分支的台账别的塔读不到 ——
看着通,实际各说各话(实测复发过不止一次)。所以:

| 改什么 | 推哪 | 怎么推 |
|---|---|---|
| **台账四件**(`docs/journal.md` · `docs/BACKLOG.md` · `docs/session-pool.md` · `docs/gate-log.md`) | **直推 `main`** | `node scripts/ledger-push.mjs "一句话说明"` |
| 别的一切(代码、skill、hook、设计文档) | **自己分支** | 照旧,合 main 要走 PR |

`ledger-push.mjs` 会体检工作区:**有台账以外的改动就拒绝跑**。代码不许借这个口子上 main。
它先把 `origin/main` 并进你的分支,再把台账整份同步过去,撞车了就报错让你手工解一次,不会静默覆盖别人写的行。
**塔醒来读台账读 `origin/main`,不是自己分支。**

> ### ★ main 上了分支保护之后:同一条命令,后半截变成你的活
>
> 保护(要求 CI 绿)一开,**直推就被拒了** —— 各塔的记账全断在这儿。脚本是**自适应**的,
> 你的命令一个字不用变,但结果有两种:
>
> | 脚本说什么 | 台账在哪 | 你还要做什么 |
> |---|---|---|
> | `✓ 台账已上 main` | **已进主干** | 没了 |
> | `⚠ 台账还没进 main`,给你一个 `ledger/…` 分支 | **还在分支上,别的塔读不到** | **开 PR 并合**,命令脚本已经打好给你 |
>
> 第二种照着打印的两步走:`create_pull_request`(base=main,head=那个 `ledger/…` 分支)→
> **`enable_pr_auto_merge`**(CI 绿了 GitHub 自己合,塔不用干等)。
> PR 报 not mergeable = 别的塔先合了它的台账,**重跑一次 `ledger-push` 就行**,别去手改 PR 分支。
>
> **怎么分辨「被规则挡了」和「别的塔抢先推了」**:脚本不读 GitHub 的错误文字(措辞会变),
> 而是 push 失败后现查 `origin/main` 的 sha 动没动 —— 动了 = 抢跑(自动重试),没动 = 规则挡的(转 PR 模式)。
> **后半截靠记性 = 必漏**(闸门8 的出处),所以上了**闸门12**:台账推成分支却没进 `origin/main`,收尾时拦一次。
> 脚本零凭据 —— 只 `git push`,GitHub 那一侧全部由塔用 MCP 工具做。
> 整条路可在本地裸仓库 + `pre-receive` 钩子里回归(`node scripts/test-ledger-push.mjs`)。

**开局同步要 merge,不能只 fetch**:`git fetch origin main && git merge --no-edit origin/main`。
`CLAUDE.md` / `.claude/skills/` / `scripts/` 都从**工作树**加载,不 merge 就读不到新的。
**harness 写完立刻合进 `main`,再说「各塔 merge 一下」** —— 顺序反了传的是空气。
台账有 `ledger-push`(保护开了之后它会让你补开一个 PR),harness 要开 PR;**手动那条最容易漏,已上闸门8 / 闸门12 在收尾时拦。**

**要给 `docs/plans/` 或别的载体开同样的口子,先问用户** —— 授权的字面范围只有上面四件。

**memory 只留跨项目的个人偏好和事实;跟本仓库有关的知识一律进仓库。**
