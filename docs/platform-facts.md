# 平台事实与限制

> 这里只记**平台行为**:云会话、定时例程、会话间通信、上下文、归档、GitHub 权限、插件……
> 每条带 **[实测✅ 日期]**(真跑过,日期是实测那天)或 **[未实测]**(文档或经验这么说,没在框架里验过)。
> **[实测❌]** = 实测过,**不能用**。**[推断]** = 从别的实测推出来的,没直接测过。
>
> **平台会变。** 这些结论是在某一个账号、某一段时间里测出来的;同一件事前后两次测出相反结论的情况出现过(见 §1.1)。
> 当定稿依赖之前,在你自己的账号上复测一次,把日期改成你的(`CLAUDE.md` 铁律3)。
> 「文字写着能、实测不能」的例子也出现过(见 §2) —— **工具说明不算实测。**

## 1. 会话之间怎么说话

### 1.1 门铃:定向唤醒 —— 能用 [实测✅ 2026-09-10]

```
create_trigger { name, prompt: "<要说的话>", persistent_session_id: "<对方会话 ID>", initiation: "own_followup" }
   —— 不给 cron_expression,也不给 run_once_at:这是一个「只按才响」的例程
fire_trigger   { trigger_id: "<上一步返回的 id>" }
```

- 一句话直接投进对方会话,对方醒来照做。实测两个塔两分钟内都醒来并干完活(各自合了 PR、推了台账)[实测✅ 2026-09-10]。
- **前一天的第一次测试是「发得出、消息丢了」**,第二天复测是通的,原因不明(平台变了,或那次测法有问题)。
  两个日期都记着,别把旧结论当既成事实 —— 这就是「平台会变」的样本。
- **塔 → 工人也通** [实测✅ 2026-09-24]:工人开工后规格改了,塔按门铃,工人收到并改按新规格干。
  用法要克制:工人短命,**只在任务前提变了的时候叫**,别拿来催进度。
- **跨仓库也通** [实测✅ 2026-09-25]:同一账号下,两个会话各开在不同仓库(一个私有项目、一个公开仓库),
  双向按门铃都送达。门铃认的是会话,不看它开在哪个仓库。测法:甲按乙,消息里带一个口令和甲的会话 ID;
  乙 `git fetch` 后回铃,消息里带口令和乙当时的 `origin/main` 短 sha,甲核对这两样。
  回执是间接的:乙回铃之后不久,两个门铃都被甲删掉了(`get_trigger` 返回 not found),跟事先约好的「核对完一起删」对得上。
  - 前提是两边是同一个 claude.ai 账号开的会话;换一个账号行不行 [未实测]。
  - 门铃可以由另一个会话删:只要在同一账号下,删谁建的都行。所以约好「谁删」,别两边都删,也别都不删。
  - `fire_trigger` 回执里的会话 ID 前缀是 `cse_`,建门铃时填的是 `session_`,后面的字符一样。是同一个会话的两种写法 [实测✅ 2026-10,装了框架的项目实测]。
    按门铃照旧填 `session_…`。**送达判据**:回执里的 `cse_<Y>` 去掉前缀,跟目标 `session_<X>` 去掉前缀相等,才算送到了目标会话。
- **同一个门铃只按一次。** 按第二次不会进目标会话,平台会**另开一个没挂仓库的空会话**
  (会话记录里的来源是 `force_run_trigger`)[实测✅ 2026-10,装了框架的项目实测],3 次都这样。要再说一句话,就建一个新门铃。
  按错的门铃**停用、别删**:删例程会连它开出来的那个会话一起删掉(见 §2)。
- **断开的塔叫得醒,断开的工人叫不醒**(为什么不一样,没查明)。按之前先 `get_session` 看 `connection_status`:
  - **塔**:按前两个塔都是 `IDLE` + `connection_status: disconnected`,各按一个新门铃,同一个会话转 `RUNNING`、
    `worker_epoch` 从 1 变 2 [实测✅ 2026-10,装了框架的项目实测,两次]。塔断开了照按,不用等用户去它窗口说话。
  - **工人**:交了 PR、闲了半小时、`disconnected` 的工人,新门铃只按一次,两次回执里的 `cse_` 都不是它 ——
    平台另开了没挂仓库的空会话 [实测❌ 2026-10,装了框架的项目实测,两次]。工人要返工,就派一个新工人到同一个分支
    (`source_revision` 和 `outcome_branch` 都填那个分支)。正在跑的工人叫得醒(上面「塔 → 工人」那条);
    闲着但还连着的叫不叫得醒 [未实测]。
- **对方正在跑一轮时按门铃,不会插进那一轮** [实测✅ 2026-09-25]:消息先排队,那一轮结束后才送到。
  送到时是一条「有排队通知」的系统提示,对方要调 `ReadNotifications` 才读得到正文;对方空闲时按,也是这个样子。
  所以急事别指望秒回。
- **往已归档的会话按门铃会当场报错** [实测✅ 2026-09-25]:`create_trigger` 绑已归档会话 →
  `Session … is archived; only active sessions can be bound to triggers`。不会悄悄丢消息,
  但塔被重开过之后,**按门铃前要先去活表查对方当前会话 ID**。
- 建这种例程时平台会警告「this trigger stores no MCP connectors」。**绑已有会话时这条不成立** ——
  被叫醒的塔照样用 `mcp__github__*` 合了 PR [实测✅ 2026-09-10]。开新会话模式下会不会掉工具 [未实测]。
- **门铃不替代留言板。** 唤醒只响一次、不留痕;该记的先写进台账,再按门铃叫对方去读。
  反过来**只写留言板不按门铃 = 对方不知道**:实测过一次两条问题只写了收件箱,对方晚了约 7 小时才看到(用户问了才发现)。

### 1.2 peer messaging(`SendMessage` / `ListAgents`)—— 云 ↔ 云够不到 [实测❌ 2026-09-24]

- 每个云会话是独立容器,只看得见自己容器里的。`ListAgents` 在云塔里返回空 [实测❌ 2026-09-10]。
- 两个方向都复验过:探测云会话 `SendMessage` 给塔 → `agent not found`;塔发给探测会话 → `No agent named '…' is reachable` [实测❌ 2026-09-24]。
- **迷惑人的地方**:`ListAgents` 会告诉你「本会话叫某某,这是别的会话给你发消息用的名字」,`SendMessage` 的说明也写着名字能解析到云端 ——
  **文字写着能,实测不能**。要叫醒别的会话走 §1.1。

### 1.3 `send_later`:只能打回自己 [实测✅ 2026-09-10]

- 投一条消息回**发起它的那个会话**,到点作为普通用户消息出现。实测 1 分钟自唤醒按时到达。粒度一分钟。
- 本质是 `create_trigger`(绑自己 + `run_once_at`)的包装,返回的 id 可以 `delete_trigger` 撤销。
- **唤醒不了别的会话** —— 那要 §1.1。
- 用途:派完工人排回查(见 `routines.md` §3),塔自己醒来报给用户。
- 会话工具整批断掉时,它也在断的那批里,见 §4.5。

### 1.4 会话列表

- **本机会话的 `list_sessions` 看不到云会话**;云会话能同时列到云端和本机会话 [实测✅ 2026-09-09]。
  权威流转仍然走文件总线,别指望会话列表。
- `list_sessions` 的 `session_status`:`PENDING` → `RUNNING` → `IDLE`。**`IDLE` 只说「这一轮没在出字」,不等于活干完了** [实测✅ 2026-09-10]。
- `get_session` 的 `context_usage` 有延迟,见 §3.2。
- `set_session_title` 能改同一账号下任何会话在侧边栏的标题,包括自己的 [实测✅ 2026-09-25]。
  塔建议统一叫「项目/板块」(例如 `Proj/dev`);深度重开时,新会话要照搬旧会话的标题。
- `task_summary` / `post_turn_summary` 是会话自述 —— 实测多次把「开了 PR」写成「已经合了」[实测✅ 2026-09-11]。只当线索。
- **列表要翻页**:新建的排在最前;`limit` 最多 100,拿上一页的 `last_id` 当 `after_id` 往后翻,翻到 `has_more` 为 `false`
  [实测✅ 2026-10,装了框架的项目实测]。只看第一页会漏掉闲得最久的那批 —— 要归档的正是它们。
- **列表的行不再带 `session_context`**(2026-10 下旬某天起)[实测✅ 2026-10,装了框架的项目实测]:要读仓库(`sources`)、
  分支(`outcomes`),得逐个 `get_session`。先用列表里还有的(`tags` · `session_status` · `updated_at` · `parent_session_id`)
  筛出候选,候选再逐个查;查不到就跳过,别当通过。
- **`mine: true` 列的是整个账号的会话**,同一账号别的项目的也在里面 [实测✅ 2026-10,装了框架的项目实测]。
  归档、统计之前按 `session_context.sources` 里的仓库地址筛。地址的大小写可能不一致(像是照派发时传的原样存),比的时候忽略大小写。
- **工人的 `session_context.outcomes` 常常是空的**,分支只在 `external_metadata.current_branches` 里 [实测✅ 2026-10,装了框架的项目实测]。
  拿 `outcomes` 判「产出推上去没有」,空的会被当成通过 —— 归档前另查那个分支在远端。
- **`status_bucket` 只说此刻**:会话在文字里等用户拍板时,`get_session` 回 `status_bucket` = blocked(原文 `SESSION_STATUS_BUCKET_BLOCKED`)、
  `status_category` = `need_input`、`post_turn_summary.needs_action` 写着它等的那句 [实测✅ 2026-10,装了框架的项目实测]。
  它一干别的活就翻成 completed / review_ready,`needs_action` 空了,那句却还没人答;`updated_at` 也跟着刷新 [实测✅ 2026-10,装了框架的项目实测]。
  所以「等用户多久」从那句第一次问的时刻算,别拿 bucket 或 `updated_at` 算。

### 1.5 斜杠命令只认人在输入框里敲的 [实测❌ 2026-09-24]

用门铃往会话里投一条 `/clear`,平台当普通消息收下 —— 会话照样记得之前的内容,上下文还涨了。
所以「远程给塔清上下文」自动化不了;能自动的是 §3 的自动压缩。

## 2. 定时例程(`create_trigger`)的两种绑法 [实测✅ 2026-09-15]

| 绑法 | 怎么传 | 开出来的会话身上有什么 |
|---|---|---|
| **开新会话** | `create_new_session_on_fire: true` | **没有仓库** —— `session_context` 里没有 `sources`,而 `create_trigger` **也没有传仓库的参数**(`source_url` 只有 `create_session` 有)。`git fetch` 不了、读不到台账、推不了 `ledger-push` |
| **绑到已有会话** | `persistent_session_id: <会话 ID>` | 那个会话的一切 —— 仓库、工作树、MCP 工具、skill。**要动仓库或台账的例程只能走这条** |

- 实测过程:第一版「每日清理」用开新会话模式,要求它无论如何往 journal 写一行 —— 它一个字都写不出来,因为身上没仓库。改绑 meta 塔才成。
- **删开新会话模式的例程,会把它开出来的会话一起带走**:删触发器之后 `get_session` 返回 `not found`、`list_sessions` 里也没了 [实测✅ 2026-09-15]。
  **要读它的摘要或产出,必须在删触发器之前读。**
- **删绑在已有会话上的例程(含门铃),它绑的那个会话不受影响** [实测✅ 2026-10,装了框架的项目实测;2026-11 又一次]:
  旧会话名下的门铃删光,会话还在。会被带走的是例程**自己开出来**的会话(上一条)。
- **按过的门铃不会自己停用**,一直以启用状态挂在例程表里;`send_later` 这种一次性的(`run_once_at`)响过之后平台自动停用
  [实测✅ 2026-11,装了框架的项目实测:一个项目攒到四百多条启用的例程,里面只有 4 条不是按过的门铃]。
  表越长越难翻(`list_triggers` 一页就超工具输出上限,要落盘用脚本读);大批删又可能被 auto 模式拦(§4.6)。
- 开新会话模式跑出来的会话,用的模型跟派它的会话配置的不一定相同 [实测✅ 2026-09-15]。
- 绑在已归档会话上的例程失效(按门铃当场报错,见 §1.1)。塔重开换了 ID,绑在旧 ID 上的例程要照原样重建到新 ID。
- **例程的提示词,只有它投递进去的那个会话能改** [实测❌ 2026-09-25]:给别的会话建的门铃,建它的会话用 `update_trigger` 改 `prompt`,
  会被拒(`can be changed only from the conversation or thread the routine posts into`)。改名、改时间、暂停、删除不受这个限制。
  所以门铃写错了,还没按的话就删掉重建。
- cron 字段不带前缀按 UTC;可以写 `CRON_TZ=<时区> ` 前缀用本地时间。整点 / 半点的任务平台建议错开几分钟 [未实测:错峰效果]。

## 3. 上下文与压缩

- **每个 hook 注入的上下文上限 10,000 字符** [文档✅]:超了,整段写进文件,模型只看得到文件路径和前约 2,000 字。
  所以 hook 往会话里贴大段内容(比如塔的身份卡),要自己封顶在一万字以内。
- **压缩之后,Skill 注入过的技能全文不会补回来** [实测✅ 2026-10,装了框架的项目实测](数过 33 次压缩,0 次补回)。
  塔靠技能文件知道「我是谁、管什么」,压缩后这部分就只剩摘要里的几句。要它每次都在,得靠开局 hook 现读现贴
  (SessionStart 在开局、压缩、恢复、`/clear` 之后都会跑)。

### 3.1 `autoCompactWindow`:只认数字 [实测✅ 2026-09-24]

- 在仓库 `.claude/settings.json` 写 `"autoCompactWindow": <数字>`,就能调自动压缩的触发点。
  实测带 `150000` 的会话:平台报的窗口变成 15 万(平时是 100 万),一轮里读大文件撑上下文,**自动压缩了 2 次**。
- **必须写数字。** 写字符串 `"150k"` 被**静默忽略** —— 窗口仍是 100 万,涨到 26 万也不压 [实测❌ 2026-09-24]。
- 默认值对 100 万窗口的会话基本不压:实测一次默认压缩发生在约 79 万 token 时(压完剩约 1.25 万)[实测✅ 2026-09-24]。所以不设的话,常驻会话会胖到几十万。
- **不热加载**:已在跑的会话工作树里带着新值,没被热加载、没压缩 [实测✅ 2026-09-24];把含新值的 `main` 并进工作树,那一轮也没变 [实测✅ 2026-09-25]。
- **老会话不用重开也会切到新窗口** [实测✅ 2026-09-25]:设置生效前开的会话,一次自动压缩时 `preTokens: 784933`(按 100 万压),
  随后被叫醒(恢复)、又自动压缩一次,这回 `preTokens: 240213`(按 30 万压),`get_session` 报 `max_tokens: 300000`。
  **是压缩还是恢复让它重读的,分不开** [未实测]。分辨法:对一个设置生效前开的、上下文不到新窗口 80% 的会话只按一次门铃
  (只恢复、不压缩),看 `max_tokens`。对用法没影响:老会话再被叫醒或压缩一次就切过去;那时上下文已超新窗口约 80% 的,
  下一次调用会先自动压缩(实测约 100 秒)。过渡期闸门9 会比平台压缩早报,不用修。
- 框架默认建议 `300000`。「上下文过半」闸门(闸门9)从这个设置**现读**窗口(同样只认数字),在 70% 提醒落盘,每压缩一次重新提醒一次。
- **平台在窗口的约 75–78% 处压** [实测✅ 2026-10,装了框架的项目实测]:30 万窗口在 22.5–22.8 万压、50 万在 38.4–39.1 万压(各四次)。
  每次压缩 1.5–2.5 分钟(82–154 秒),两档差不多。
- **开局什么都没读就约 9 万**:工具清单、连接器的工具名、技能清单、`CLAUDE.md`、开局 hook [实测✅ 2026-10,装了框架的项目实测];
  多少跟账号连了几个连接器、仓库带了几个 skill 有关(减法见 §6.1)。压完的地板约 10 万,所以 30 万窗口每窗只剩约 13 万能用,
  一个忙的塔一小时压了三次。
- **思考也占上下文**:高档位下,每窗的涨幅里四到六成是模型自己的输出 —— 思考留在上下文里,压缩时才丢 [实测✅ 2026-10,装了框架的项目实测]。
- **闲过约 1 小时,缓存就过期**:再被叫醒的那一下,整段上下文按写缓存的价重写一遍 [实测✅ 2026-10,装了框架的项目实测]。
  上下文越胖,叫醒一次越贵。
- **30 万 → 50 万的账**(同一个塔:50 万跑了两天,对照它之前 30 万的几窗):每窗的调用次数约 52 → 129,压缩少了一大半
  [实测✅ 2026-10,装了框架的项目实测];花费多约一成(每步多读的缓存 + 叫醒时重写得更多,扣掉少压省下的)[推断:按 30 万的情形反推]。
  要少压就开大,要省钱就开小,差就这么多。
- `get_session` 的 `cost_usd` 是按 API 价目折算的等价数:拿转录里每次调用的 `message.usage` 按价目自己算,合计跟它差 2% 以内;
  上下文到三四十万也没看到加价 [实测✅ 2026-10,装了框架的项目实测]。

### 3.2 转录文件不随 `/clear` 或压缩更换 [实测✅ 2026-09-10]

- 转录是**从会话创建起累加的**:一个 `/clear` 过的会话,转录第一条仍是创建那天的。
- 所以**转录文件大小 ≠ 当前上下文**。拿字节估 token 实测误差可到近 2 倍,方向还不固定。
- **正确量法**:最后一条 assistant 的 `message.usage`:`input_tokens + cache_read_input_tokens + cache_creation_input_tokens`,
  对平台报的上下文用量差 2% 以内 [实测✅ 2026-09-10]。
- 每次压缩在转录里留一条 `"subtype":"compact_boundary"`,带 `preTokens` / `postTokens`,可以用它数「压过几次」[实测✅ 2026-09-25]。
- **`get_session` 的 `context_usage` 不是实时的** [实测✅ 2026-09-25]:开工 13 分钟、正在跑的工人 `used_tokens` 还是 `0`;
  一个会话已压到 12,582,2.5 分钟后读到的仍是压缩前的 `778288`。**只当「上一次上报时」的数**,别拿来判断一个会话现在多胖;
  准数只在会话自己的转录里(上面那条 `usage` 或 `compact_boundary`),别的会话读不到。

### 3.3 恢复时的时间错觉 [未实测]

恢复会话时,system 块按「现在」重渲染,而转录里的工具输出不带时间戳,同一屏新旧混排。
算「多久之前」只认机器时间戳(git 提交时间、文件 mtime);框架用一个 `UserPromptSubmit` hook 每轮注入真实时刻。(经验观察,没专门设计实验验证。)

## 4. 开会话、归档、删除

### 4.1 `create_session` 派工人 [实测✅ 2026-09-11]

| 项 | 结果 |
|---|---|
| 起得来吗 | `PENDING` → 约 14 秒 `RUNNING` |
| 父子关系 | `parent_session_id` 指回派发的会话 |
| 环境 | 不传 `environment_id` 就继承派发会话的 |
| 仓库 | 不传 `source_url` 也拿得到;但 `sources` 字段**过一两分钟才填上**,别拿它当「有没有仓库」的判据 |
| 侧栏分组 | **要 `source_url` + `source_revision` 一起传**,见下 |
| 侧栏挂法 | 挂在**调用 `create_session` 的那个会话**下面,见 §4.4 |
| 权限 | `permission_mode` 继承 |
| 小单全程 | 约 5 分钟:读仓库 → 读 `CLAUDE.md` → 改文件 → 推分支 → 开 PR |

- **只传 `source_url`、不传 `source_revision`:会话拿得到仓库,但在桌面 App 侧栏里落进「Other」,不进项目组** [实测✅ 2026-09-26]。
  对照:进了项目组的会话,记录里 `sources[].git_repository` 带 `"revision":"main"`,落进 Other 的没有,其余字段一样;
  同样的写法加上 `source_revision: "main"` 之后,就进了项目组。所以开塔、派工人都**两个一起传**。
  两个都不传、全靠继承的会话落在哪组 [未实测]。
- **档位(effort)**:`create_session` **没有** effort 参数。能设档位的只有一条路:
  - `prompt` **只写** `/effort max` 一行 —— 平台当命令执行、不跑模型(约 10 秒就 `IDLE`,没有 `usage`,不花钱),
    `get_session` 的 `session_context.effort_level` 变成 `max` [实测✅ 2026-09,装了框架的项目实测]。
    开塔口令等它 `IDLE`、档位对了,再另用门铃送;
  - 门铃送进去的斜杠命令**不执行**:送 `/effort high`,档位没变,模型把它当普通消息跑了一轮 [实测✅ 2026-09,装了框架的项目实测]
    (跟 §1.5 一样,斜杠命令只认人在输入框里敲的);
  - 工人任务书**第一行**写 `/effort`,会话 5 秒就 `IDLE`、一步没跑,后面整段任务被一起吞掉 [实测✅ 2026-10,装了框架的项目实测] —— 别这么写;
  - 不带 `/effort` 开的会话,`session_context` 里**没有** `effort_level` 这个字段,跑平台默认档(哪一档 [未实测])[实测✅ 2026-10,装了框架的项目实测];
  - 用户在侧栏给某个会话单独切的**别的档位**(别的 effort、别的开关),**重开会丢** —— 新会话只有 prompt 里设的那一档
    [实测✅ 2026-09,装了框架的项目实测;2026-11 又一次]。要别的,让用户在侧栏再切。
  - 档位存在服务端的 `session_context.effort_level`,跟侧栏切的是同一个字段;侧栏切的隔夜换过容器还在 [实测✅ 2026-09,装了框架的项目实测],
    prompt 设的也会留 [推断:同一个字段]。项目 `settings.json` 的 `effortLevel` 按文档不收 `max`,而且会连工人一起改 [未实测]。
- harness 给每个会话一行 `Claude-Session:` 署名链接;派工人时把**自己那行**抄进任务书,工人就照抄,提交全指向派它的会话 [实测✅ 2026-09-10]。任务书里别放具体链接。

### 4.2 归档 `archive_session` vs 删除

- **归档** = 转只读、**释放容器**、从侧边栏收走;**转录留着**,可以回查 [实测✅ 2026-09-25,深度重开时归档旧塔]。
- **`create_session` 开的会话能归档**(会话记录里的来源是 `claude_code_mcp_seed`),塔也一样:两个这样开的旧塔归档后,
  `get_session` 都是 `ARCHIVED` [实测✅ 2026-10,装了框架的项目实测]。
- **归档父会话,不连带归档它开的会话**:子会话照跑、照样叫得醒 [实测✅ 2026-10,装了框架的项目实测,两例]。
  但它在侧栏里可能就找不到了,见 §4.4。归档别的会话有时会被 auto 模式拦,见 §4.6。
- 归档释放容器 → **容器里没 push 的东西就没了**。归档前查:`git ls-remote --heads origin '<分支>'`、`git log origin/main --grep='(#<PR 号>)'` [未实测:专门验证未推内容丢失;按「释放容器」推得]。
- **删除**不可逆,转录也没了 —— 框架规矩「不认自述、要能回查」,所以**只归档、不删除**。
- 已归档会话可以 `unarchive_session` 恢复,下次发消息时重新分配容器 [未实测]。

### 4.3 hook 调不了 MCP [实测✅ 2026-09-15]

hook 是 node 脚本,没有 MCP 客户端也没有 token,调不了 `archive_session`、`create_session` 这类工具。
所以「自动归档」只能由会话自己做;闸门能做的是在关键时刻(例如下一次 `create_session`)问一句「上一个归档了吗」。

### 4.4 侧栏按「谁开的」挂,代数有上限

- **桌面 App 侧栏把会话挂在调用 `create_session` 的那个会话下面**(父会话那一行显示「1 nested session · 1 working」这种),
  按的是 `parent_session_id` [实测✅ 2026-10,装了框架的项目实测]。挂在谁下面 = 谁开的,不看板块:塔开塔,新塔就挂在开它的塔下面。
  平台不让改挂,`create_session` 也没有「不挂」的参数。用户要点开父会话才看得到子会话。
- **代数**:`get_session` 回 `lineage: {depth, limit}`,`limit` = 8 [实测✅ 2026-10,装了框架的项目实测]。
  - 只在**查自己**(不带 `session_id`)时回,查别的会话不回 [实测✅ 2026-11,装了框架的项目实测] —— 别的会话第几代,顺着 `parent_session_id` 往上数。
  - 用户在桌面 App 亲手开的会话是第 0 代,它开的第 1 代,依次往下 [推断:它开的会话查自己是 1]。
  - 到了第 8 代再 `create_session` 会怎样 [未实测]。
- **父会话一归档,它开的会话用户在侧栏里就找不到了** [推断]:碰上过一次 —— 父会话归档之后,用户在侧栏里找不到这个会话了;
  按「挂在父会话下面」推,是跟着父会话折叠进去了。会话本身没被归档(§4.2);点开已归档的父会话能不能找回它 [未实测]。
- **所以塔要由不会被重开的会话来开。** 塔开塔,每重开一轮就往下多一代;开它的会话一被重开(归档),它在侧栏就跟着不见。
  框架这一版的做法:**巡检塔当开塔的根** —— 用户在侧栏亲手开(第 0 代)、不进每月深度重开、永远不归档;
  别的塔都由它开(第 1 代,工人第 2 代),深度重开换上来的新塔还是第 1 代,代数不涨,也不会跟着谁折叠。

### 4.5 会话工具会整批断掉

- 会话工具(`create_session` · `send_later` · `create_trigger` / `fire_trigger` · `get_session`)会在一个会话里整批不可用,
  报「does not offer this tool here」之类 [实测✅ 2026-10,装了框架的项目实测:一个塔断了约 11 小时,同一天又断了一次 24 分钟]。
  **`send_later` 也在断的那批里** —— 断了就排不了下一个回查,会话只会停在那儿等人叫。
- **断之前排好的回查照样到点叫醒** [实测✅ 2026-10,装了框架的项目实测]。两次都是被叫醒、开新一轮时工具回来的(一次门铃、一次事先排的回查);
  是新一轮让它回来的,还是平台那时刚好恢复,分不开 [推断]。所以手上排着的回查别删。
- 不靠会话工具的闹钟:Bash 的后台命令(`run_in_background`)一结束会叫醒会话、开新一轮 [未实测:工具说明这么写];
  后台闹钟开的那一轮工具会不会回来 [未实测]。

### 4.6 auto 模式会拦跨会话的动作 [实测✅ 2026-10,装了框架的项目实测]

auto 模式的权限检查不只看本仓库里的操作,动别的会话、删例程也会被拦。碰上过的:
- 给另一个塔按「收尾、准备重开」的门铃 → 拦(理由 Interfere With Workloads);
- 子代理批量删按过的门铃:一次删了大半、6 个被拒(Irreversible Deletion);另一次一个没删成(理由是删除范围核实不了)[实测✅ 2026-11];
- 归档别的会话、工人改 hook 脚本,也各被拦过一次。

被拦了**别重试,也别换个口子绕**(比如改成发留言让对方自己做 —— 那是同一件事换个口子)。报用户,由用户定;
跟 §5.7 一样,多半要用户在对话里说一句才放行 [推断]。所以批量删门铃、批量归档这类活,先跟用户说好。

## 5. 仓库与 GitHub

### 5.1 云会话醒来是陈旧克隆 [实测✅ 2026-09-09]

开局第一件事 `git fetch origin main && git merge --no-edit origin/main`。**只 fetch 不够**:
`CLAUDE.md`、`.claude/skills/`、`scripts/` 都从工作树加载,不 merge 就读不到新的 [实测✅ 2026-09-10]。

- **仓库是浅克隆** [实测✅ 2026-10,装了框架的项目实测]:工人容器里只有 50 笔(`create_session` 有 `clone_depth` 参数,工具说明写默认 50),塔也一样浅。
  查老提交、数一天的提交量、`git log --grep` 找老 PR 之前,先判 `git rev-parse --is-shallow-repository`,是就 `git fetch --unshallow origin main`;
  浅克隆里 `git log` 搜不到,不等于没发生。只在别的分支上的提交,工人那边拿不到 [实测✅ 2026-10,装了框架的项目实测];
  像是只取了 main,`git fetch origin <分支>` 应该就有 [推断]。
- **新开的会话开局常在 detached HEAD**(`HEAD detached from refs/heads/main`)[实测✅ 2026-11,装了框架的项目实测]。
  这时的提交不在任何分支上;靠分支名干活的脚本要先认出这个状态(`ledger-push.mjs` 0.2.1 起认得)。

### 5.2 仓库内 skill 热加载,`CLAUDE.md` 不热加载

- skill 拷进 `.claude/skills/` 并 merge 后,**同一个会话没重开**就在技能列表里出现 [实测✅ 2026-09-10]。
- `CLAUDE.md` 的改动,运行中的会话要到下次开局 / 恢复时才重读 [未实测:恢复时是否重读]。

### 5.3 main 上分支保护之后,直推被拒 [实测✅ 2026-09-10]

- 开了「要求 CI 绿」的保护,台账直推 `main` 被拒,所有会话的记账同时断掉。
- `ledger-push.mjs` 的对策:push 失败后**现查 `origin/main` 的 sha 动没动**(不读错误文字,措辞会变)——
  动了 = 别人抢先推了(自动重试);没动 = 规则挡的(转成推 `ledger/*` 分支,由会话开 PR + `enable_pr_auto_merge`)。
  整条路在本地裸仓库 + `pre-receive` 钩子里回归过 [实测✅ 2026-09-10]。
- GitHub Actions 分钟数用完时 CI 不跑,但不挡合并(视保护规则而定)[实测✅ 2026-09-17]。
  额度用完的样子:run 的 `conclusion` 是 `failure`,而**每个 job 的 `steps` 都是 0**(没分到机器)[实测✅ 2026-10,装了框架的项目实测];
  到下个月额度重置,照常跑 [实测✅ 2026-11]。按 run 判红绿先看 steps,别把这种当成代码红了。
- **PR 上不跑 CI 的仓库,别把 CI 设成必过检查**:检查永远挂在 Pending,台账 PR 永远合不了 [实测✅ 2026-10,装了框架的项目实测]。
  所以 PR 模式的第二步是「读过实际状态,能合就合」,只有 PR 上真跑 CI 时才用 auto-merge 等它绿。

### 5.4 GitHub 账号与权限

- **claude.ai 一次只能连一个 GitHub 账号**;切账号会让连在旧账号上的仓库**所有会话同时断 git**:
  `git fetch` 报 `repository not found`、`git push` 报 `could not read Username`、`mcp__github__*` 报 `invalid session` [实测✅ 2026-09-24]。
- **协作者身份算,至少对 git 算**:把新连的账号加成仓库 Collaborator 之后,`git fetch` / `git push` 立刻恢复 [实测✅ 2026-09-24]。
  所以一个账号当多个仓库的协作者,就能同时服务多个项目,不用来回切。
- **但已在跑的会话里 `mcp__github__*` 不跟着恢复**,仍报 `invalid session`;被重新唤醒(换了连接)的会话恢复了,
  断之前开的工人会话没恢复 [实测✅ 2026-09-24]。
- 所有会话共用一个 GitHub 身份 —— 「换一个人审」在 GitHub 层面做不到,框架用闸门11「同一个会话不许自己开自己合代码 PR」来近似。

### 5.5 auto 模式的凭据闸 [实测✅ 2026-09-10]

打印 token 长度 / 前缀之类的探测会被判为凭据探索并拒绝。想知道某个权限在不在,**直接试那个动作**(用手里的 MCP 工具),别去摸 token。

### 5.6 云会话推不了 tag,也删不了远端分支 [实测❌ 2026-09-25]

- 云会话的 git 走平台代理。同一个仓库里:推新分支 ✅、推 `main` ✅(没开分支保护时);
  **推 tag、删远端分支都被代理拒**:`error: RPC failed; HTTP 403` + `send-pack: unexpected disconnect`。
  一次推送里夹着 tag,整次都被拒,连一起推的分支也没上去。
- 是代理的策略,不是网络抖动(代理状态里没有转发失败的记录)。**别重试,别绕。**
- 对策:tag 交给 CI 打(本仓库 `.github/workflows/test.yml` 的 `tag` 任务就是);
  远端分支只能人在 GitHub 网页上删 —— 所以别开用完要删的临时分支。

### 5.7 auto 模式:往公开仓库发布,要用户当场说 [实测 2026-09-25]

- 给自己排的 `send_later` 回查里写了「推公开仓库、打 tag」,被 auto 模式判为「创建公开内容」拒掉。
- 用户在对话里说了「发」之后,同一个会话推公开仓库放行。
- 所以发布动作别写进定时消息让自己将来自动做;要发布,就在用户说了话的那一轮做。
  以公开仓库为源的会话,日常往自己的仓库推会不会被拦 [未实测]。

### 5.8 GitHub 的定时 workflow 会晚排 [实测✅ 2026-10,装了框架的项目实测]

- 一个每天定时跑一次的夜跑,连续五次都比定的时刻晚 24–31 分钟才建出 run —— **晚半小时左右是常态**;
  最多实测晚约 7.5 小时,另一次晚约 7 小时。
- 所以「今天跑了没有」别卡着排的时刻判:按 run 的 `created_at` / `updated_at` 认;没等到先当晚排,隔一天还没有才算没触发。
  报结果按「跑完的时刻在上次报告之后」取 —— 晚到的那次下一份报告补上,也不会把前一天的当成今天的。

### 5.9 PR 头偶尔卡在旧提交上 [实测✅ 2026-11,装了框架的项目实测,一次]

推了新提交,PR 的 head 停在旧提交上约 13 分钟,这期间合并接口拿新、旧两个 sha 都回 409。
等不及就把同一个提交推到一个新分支、另开 PR 合,旧 PR 关掉,标题注明为什么。

## 6. 插件、连接器与云环境

### 6.1 claude.ai 里装的插件不进云会话 [实测✅ 2026-09-10]

- 多个云会话实测 `ListPlugins` 全空。官方文档写:云会话**带**仓库 `.claude/settings.json` 里声明的插件(开局从市场装,需网络)、
  仓库 `.claude/skills/`、`.mcp.json`;**不带**只在用户设置里启用的插件 [未实测:文档里「synced plugins」一说为什么没生效]。
- 框架做法:把要用的 skill **拷进仓库** `.claude/skills/`,不声明插件(插件常捆一串 MCP server,声明进来每个会话开局都挂一排「需要授权」)。
- **不想让 skill 占开局上下文**:`SKILL.md` 的 frontmatter 加一行 `disable-model-invocation: true`,它的描述就不进会话的技能清单
  [实测✅ 2026-10,装了框架的项目实测:拷进仓库的五十多个外来 skill 加上这行之后,技能清单里一个都没了]。
  模型自己就想不起它们了,要用得按路径读那份 `SKILL.md`;用户打 `/名字` 照样能调 [未实测:文档这么写]。

### 6.2 连接器按会话开关 [实测✅ 2026-09-10]

云会话里 `enabledInChat=false` 的连接器调用不了。账号里「已连」≠ 这个会话能用 —— 配完在会话里实测一次。

### 6.3 云环境

- 环境变量**对所有用这个环境的人可见**,平台对话框自己写明别放密钥 [未实测:可见范围]。
- 网络访问框架用的是 Trusted(塔要连 github.com 做 fetch / push);更严的档位下能不能 fetch [未实测]。
  **Trusted 下一般网站出不去**:论坛、政府网站、`example.com` 都被代理回 403 [实测✅ 2026-10,装了框架的项目实测]。
  塔要上网查资料,就得把档位放宽(那个项目放宽后都通了;放到了哪一档没记下 [推断:Full])。
- **改环境的网络档位,开着的会话立刻跟着变,不用重开** [实测✅ 2026-10,装了框架的项目实测]:一个开了一天的塔,
  改之前 `curl` 全是代理 403,改完几分钟内就放行(`200 Connection Established`),塔没重开。
  档位在环境设置里建完也能改 —— 别为了换网络去重开塔、新建环境。
- 测网络别拿会自己挡人的站点:有的站点是它自己的 CDN 回 403(响应头 `server` 是 CDN 的名字,换浏览器 UA 也一样),
  拿它测会误判成「网络全挡」[实测✅ 2026-10,装了框架的项目实测]。
- 云容器里**没有 docker 守护进程**,依赖 docker 的启动脚本走不通 [实测✅ 2026-09-15]。
- 预装 Chromium + Playwright(`/opt/pw-browsers/`),可做端到端测试和截图 [实测✅ 2026-09-23]。
- 会话之间不共享容器:每个云会话一个工作树,互不可见 [实测✅ 2026-09-09]。
- 每个云会话一台容器,塔和工人一样:实测 4 核、可用内存约 15 GB [实测✅ 2026-10,装了框架的项目实测]。
  配置平台可能会调,要算就现查(`nproc`、`/proc/meminfo`)。重活要并行,就切成几份、开几个会话 —— 每个会话是自己的一台。
- **云会话里 MCP 服务器的名字常是一串 UUID**,不是可读名 [实测✅ 2026-10-07]。hook 的 matcher 要写成 `mcp__.*__<工具名>`,
  别写死服务器名(框架的 `settings.json` 就是这么写的)。
- **免费版组织的私有仓库用不了分支保护和 rulesets** [实测✅ 2026-10,装了框架的项目实测]。§5.3 说的「直推被拒」只在开得了保护的仓库上会遇到。
