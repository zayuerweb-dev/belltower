# 例程配方:每日清理 · 每周深度重开 · 派工后 10 分钟回查

三个例程让用户**不用盯着**这套机器:工人跑完自己被收走、塔的上下文每周清一次、派出去的活塔自己回查自己报。
下面每个都给:**干什么 → 可直接粘贴的提示词 → 怎么建**。

> 提示词里的 `<…>` 是占位,建之前换掉。**提示词里不要写死任何会话 ID 或例程 ID** —— 塔会重开换 ID,
> 写死的 ID 一定会烂(「派生 > 存储」)。要 ID 的地方写「去活表查」。

---

## 0. 先搞清两件事

### 0.1 为什么绑在 meta 塔上,不开新会话

`create_trigger` 有两种绑法(详见 `platform-facts.md` §2)[实测✅ 2026-09-15]:

| 绑法 | 参数 | 身上有没有仓库 |
|---|---|---|
| 开新会话 | `create_new_session_on_fire: true` | **没有** —— `create_trigger` 没有传仓库的参数,开出来的会话 `git fetch` 不了、读不到台账、推不了 `ledger-push` |
| 绑已有会话 | `persistent_session_id: <meta 会话ID>` | **有** —— 那个塔的仓库、工作树、MCP 工具、skill 全在 |

三个例程都要读写台账,所以**只能绑已有会话**。绑 meta 塔是因为这三件事都是「会话这台机器本身」的事,归 meta 板块。
实测教训:第一版每日清理用开新会话模式,要求它每次往 journal 写一行 —— 它一个字都写不出来。

另一条:**删开新会话模式的例程会把它开出来的会话一起带走**,要读试跑结果先读再删 [实测✅ 2026-09-15]。

### 0.2 绑的 ID 会变

meta 塔自己被重开过(用户手动)之后,旧 ID 已归档,绑在上面的例程**会失效**(按门铃当场报错)[实测✅ 2026-09-25]。
所以 meta 换会话后:`list_triggers`(带 `include_completed: true`)找出 `persistent_session_id` = 旧 ID 的,照原样(cron / prompt)绑到新 ID 重建,再删旧的。
「每周深度重开」对别的塔做同样的事(§2 步骤 6)。

## 1. 每日清理:把跑完的工人归档

**干什么**:扫一遍会话,把跑完、产出已安全落地的工人会话 `archive_session` 掉。
**为什么要每天**:工人收完活就该归档(`dispatch.md` §6),但靠塔记得 = 必漏;侧边栏会越积越长,容器也不释放。

### 1.1 提示词(粘贴进 `prompt`)

```
【每日清理】这一轮只做清理这一件事,做完接着干你原来的活。
把跑完、产出已安全落地的工人会话归档掉。四条判据全中才动,缺一条就跳过:
1. tags 含 worker —— 没这标签的是塔,永远不许动。
2. 状态不是 RUNNING,也不是已经 ARCHIVED。
3. updated_at 距现在 ≥ 24 小时 —— 给派它的塔留一天收活。
4. 产出已在远端:拿 session_context.outcomes 里的分支名跑 git ls-remote --heads origin <分支>,查到才算;它压根没有分支就算通过。
三条绝不:
- 绝不用删除,只用 archive_session(不认工人自述、要能回查,转录必须留);
- 绝不动塔;
- 绝不动 RUNNING 的(归档释放容器,没 push 的东西会没)。
步骤:list_sessions(mine:true, limit:30)→ 逐个判 → 满足的 archive_session
→ git fetch origin main && git merge --no-edit origin/main
→ docs/journal.md 追一行 → node scripts/ledger-push.mjs "每日清理:归档 N 个工人"。
被归档的工人若在 docs/session-pool.md 任务会话表里还挂着行,在 journal 里点名提醒派它的塔,
不要替它删队列行(派发权归执行方)。
跑完必须报给用户,一张小表,不管有没有归档:
  每日清理 · <日期>
  扫了 N 个会话 · 归档 M 个 · 跳过 K 个
  归档:Qxxx 某某任务(闲了 31 小时,分支在远端)· …
  跳过:Qxxx(还在跑)· Qxxx(闲了 6 小时,不够 24)· …
归档 0 个也要报。journal 只在真归档了才写(0 个不留台账噪音),但跟用户的话每天都要说。
```

### 1.2 怎么建

```
create_trigger {
  name: "每日清理工人会话",
  cron_expression: "CRON_TZ=<你的时区> 52 3 * * *",     # 每天凌晨,错开整点
  persistent_session_id: "<meta 会话ID>",                # 去 docs/session-pool.md 塔表 meta 那行查
  prompt: <上面 1.1 全文>,
  initiation: "human_request"                            # 用户要求建的就写这个
}
```

- cron 不带 `CRON_TZ=` 前缀按 UTC(例如 `0 8 * * *` = UTC 08:00)。挑一个塔们大概率闲着的时段。
- 判据第 1 条依赖**派工人时打 `worker` 标签**(`dispatch.md` §4:`tags: ["worker", "Qnn", "<板块>"]`),
  **开塔时不打**(`tags: ["tower", <板块>]`)。标签打错,这个例程就会误伤塔 —— 所以「绝不动塔」写了两遍。
- 建完可以 `fire_trigger` 手动试跑一次,看报表。

## 2. 每周深度重开:清掉压缩摘要里攒的偏差

**干什么**:对每个塔做「收尾 → 归档 → 重开」。
**为什么**:上下文维护分两层 ——
**第一层**是自动压缩(`.claude/settings.json` 的 `"autoCompactWindow": 300000`,**必须是数字**,见 `platform-facts.md` §3.1),天天自己跑;
**第二层**是这个例程:压缩摘要一轮轮叠下去会慢慢走样(典型症状:塔忘了自己是塔,开始自己干成品活),每周从台账冷启动一次清掉。

**规矩只存一份**:例程提示词只写「照 `tower.md`〈每周深度重开〉那一节做」,判据和步骤只在那一节改。
下面 §2.2 把那一节的要点抄过来给你看懂,**建例程时不要把它们抄进提示词**。

### 2.1 提示词(粘贴进 `prompt`)

```
【每周深度重开】
先 git fetch origin main && git merge --no-edit origin/main,然后照
.claude/skills/tower-meta/references/tower.md「每周深度重开」一节逐步做 ——
判据、步骤、门铃原文都只在那一节维护,这里不抄第二份(规矩只存一份)。
几条别忘:
- meta 自己不重开(本例程就绑在 meta 上)。
- 判据有一条不中就跳过并报给用户,不硬来。
- 归档是 archive_session,绝不删除。
- 重开之后活表换新 ID(ledger-push),绑在旧会话上的例程照原样重建到新 ID。
- 收尾回查排 20 分钟(send_later 打回 meta),没回 HANDOFF-READY 的这周跳过。
跑完必须报给用户一张表:谁重开了(侧边栏新会话名)、谁跳过了(为什么)、这一轮花了多少。
journal 记一行,ledger-push。
```

### 2.2 `tower.md` 那一节的要点(看懂用,不进提示词)

**谁会被重开**(三条全中才动):
1. 塔表里有会话 ID 的塔,**meta 自己除外**(meta 靠自动压缩;要全新就让用户手动 `/clear` —— 远程发 `/clear` 不生效 [实测❌ 2026-09-24])。
2. **这一周有过动静**(`updated_at` 在 7 天内)—— 一周没动的塔没攒偏差,重开白花钱。
3. **现在闲着**:塔不是 `RUNNING`;它派的工人(`parent_session_id` = 它)没有 `RUNNING` 的;6 小时内没动过(用户可能刚跟它聊完)。

**步骤**:
1. **收尾 —— 按门铃**:`create_trigger`(`persistent_session_id` = 那个塔)+ `fire_trigger`,内容:
   「【每周深度重开 · 收尾】把进行中的讨论、等用户答的问题、排着的回查(send_later)、在跑 / 待收的工人
   写进台账(journal 一行 + 该进 BACKLOG 的进 BACKLOG);该推的推、该合的合。最后一行只写 `HANDOFF-READY`。」
2. 排一个 20 分钟回查(`send_later`,打回 meta)。回查时逐个 `get_session`:`IDLE` 且摘要 / 最后一行有 `HANDOFF-READY` → 往下;没有 → 这周跳过,报给用户。
3. **归档旧会话** `archive_session` —— 不删除,转录要能回查。
4. **开新会话** `create_session`:`source_url` 本仓库、`source_revision: main`、`title` = 塔名、
   `tags: ["tower", <塔名>]`(**不带 `worker`**;旧会话上平台自动加的 `config:*` 标签不用照搬);`prompt` = 开塔口令一行 + 「上一任的接手须知在 journal 里本塔最新一条」。
5. **更新活表**:塔表那一行换成新会话 ID,`ledger-push`。
6. **处理绑在旧会话上的例程**:`list_triggers` 带 `include_completed: true` 全翻(不带会漏跑完的一次性回查;
   输出超上限就落盘用脚本读,条目在 `data` 下,翻页看 `has_more` / `next_cursor`),挑 `persistent_session_id` = 旧 ID 的:
   定时例程 → 照原样绑到新 ID 重建再删旧的;还没响的一次性回查 → 一样搬 [未实测];按过的门铃 → 直接删不重建;
   响过的一次性回查 → 平台已停用,不管。详见 `tower.md` 同一节第 6 步。
7. **报给用户一张表**:谁重开了、谁跳过了(为什么)、花了多少。

**会丢的**:会话 ID(按门铃前查活表)· 用户在侧边栏跟旧塔的聊天窗口(变只读,内容都在)·
用户手动给塔设的档位(`create_session` 设不了)。
**代价**:每个塔收尾一轮(按当时上下文大小)+ 开局一轮(实测约 $0.6、34 秒,开局就占约 10 万上下文)[实测 2026-09-25]。

### 2.3 怎么建

```
create_trigger {
  name: "每周深度重开",
  cron_expression: "30 8 * * 0",                         # 每周日 08:30 UTC;或 "CRON_TZ=<你的时区> 30 4 * * 0"
  persistent_session_id: "<meta 会话ID>",
  prompt: <上面 2.1 全文>,
  initiation: "human_request"
}
```

- 选一个用户和塔大概率都闲着的时段(周末凌晨)。判据 3 会自动跳过正在忙的塔。
- **首次跑建议人在场**:手动 `fire_trigger` 一次,对一个塔走完全程,确认新塔开局能认出自己、台账能接上,再交给 cron。
- 重开之后新塔开局 hook 靠活表里的新 ID 认身份;活表更新之前,开塔口令里写了板块,不影响。

## 3. 派工后 10 分钟回查:用户不用问「现在谁在跑」

**干什么**:塔派完工人,**同一轮里**排一个 10 分钟后的自唤醒;到点塔自己查工人和 PR,自己报给用户。
**为什么**:工人是另开的会话、另一个容器,用户在塔的窗口里**一个都看不到**(`CLAUDE.md` 铁律7)。
本地那种「能直接看到在跑」的是同一会话里的子代理,跟云工人结构上不同,改不了;能改的是「要用户来问」。

这个不是定时例程,是**一次性自唤醒**,用 `send_later`(它只能打回发起它的会话 —— 正好落在塔自己身上)[实测✅ 2026-09-10]。

### 3.1 怎么排(派工人的同一轮里)

```
send_later {
  delay_minutes: 10,
  name: "回查 Qnnn",
  initiation: "own_followup",
  message: <下面 3.2 全文,换掉占位>
}
```

### 3.2 提示词(粘贴进 `message`)

```
【回查 Qnnn】<一句话说清这单是什么>。工人会话:<派的时候 create_session 返回的 ID>,分支:claude/qnnn-<短标题>。
醒来做四件:
① get_session / list_sessions 查工人状态 —— IDLE 只说「这一轮没在出字」,不等于干完;
② list_pull_requests 查 PR 开没开、合没合 —— 不认工人自述(实测多次把「开了 PR」写成「已经合了」);
③ 没跑完就再排一个 10 分钟;跑完就按 dispatch.md §6 收活:核 diff(文件域有没有越界、台账四件有没有被碰、
   读 patch 不读描述)→ 合 PR 或提修改 → 删活表那行 → journal 一行 → 确认分支已在远端后 archive_session;
④ 把结论报给用户,一行一个工人,不要问「要不要我继续」。
```

> 这里写工人会话 ID 没问题 —— 它是塔**这一轮刚拿到的**,10 分钟后用,不是写死在仓库里的状态。

### 3.3 三条别搞错

1. **`send_later` 唤醒不了别的塔**,只打回自己。要叫醒别的塔用门铃(`create_trigger` 带 `persistent_session_id` + `fire_trigger`)。
2. **间隔照活的长短定。** 实测小单工人全程约 5–20 分钟,**首次 10 分钟**合适;没跑完再排一个,别 1 分钟一次空转烧钱。
3. **醒来先查 GitHub 再信摘要。**

### 3.4 报给用户的格式

```
Q301 dev  <一句话任务>     在跑   <它在干嘛>          —           $2.1
Q101 plan <一句话任务>     跑完   PR 开着 668 行      等 plan 收  $4.7
```

一行一个工人,别贴 JSON。报号带一句话内容(铁律5)。

## 4. 例程的维护

- **列出来**:`list_triggers`;要看某个例程当前的 prompt 和绑定,用 `get_trigger`。
- **改提示词 / cron**:`update_trigger`,不要删了重建(会丢运行历史)。**例外**:要换绑定的会话 ID 只能重建(见 §0.2)。
- **这三个例程是用户要的才建**:建的时候 `initiation` 写 `human_request`,并在 journal 记一行用户原话 + 时刻(`CLAUDE.md` 铁律6 —— 塔不许自己加例程烧钱)。
- 例程跑的结果要**报给用户**,不管有没有事 —— 用户看不见后台,沉默会被当成「没在跑」。
