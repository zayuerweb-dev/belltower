# 例程配方:巡检塔每日 · 每月深度重开 · 派工后 10 分钟回查

三个例程让用户**不用盯着**这套机器:巡检塔每天收工人、看昨晚定时 CI、把查出来的派回该管的塔;塔的上下文每月清一次;派出去的活塔自己回查自己报。
前两个是定时例程,绑在巡检塔上;第三个是塔派完工人给自己排的一次性回查。
下面每个都给:**干什么 → 可直接粘贴的提示词 → 怎么建**。

> 提示词里的 `<…>` 是占位,建之前换掉。**提示词里不要写死任何会话 ID 或例程 ID** —— 塔会重开换 ID,
> 写死的 ID 一定会烂(「派生 > 存储」)。要 ID 的地方写「去活表查」。
>
> **提示词只写「照哪份文件做」+ 几条别忘**,做法只在仓库里存一份:每日的在 `patrol.md`,每月的在 `tower.md`「每月深度重开」
> (两份都在项目的 `.claude/skills/tower-meta/references/` 下,是框架文件,`belltower-sync` 会更新)。改做法改那两份,例程一个字不用动。

## 0. 先搞清三件事

### 0.1 为什么绑在巡检塔上,不开新会话

`create_trigger` 有两种绑法(详见 `platform-facts.md` §2)[实测✅ 2026-09-15]:

| 绑法 | 参数 | 身上有没有仓库 |
|---|---|---|
| 开新会话 | `create_new_session_on_fire: true` | **没有** —— `create_trigger` 没有传仓库的参数,开出来的会话 `git fetch` 不了、读不到台账、推不了 `ledger-push` |
| 绑已有会话 | `persistent_session_id: <巡检塔会话ID>` | **有** —— 那个塔的仓库、工作树、MCP 工具、skill 全在 |

两个定时例程都要读写台账,所以**只能绑已有会话**。
实测教训:第一版每日清理用开新会话模式,要求它每次往 journal 写一行 —— 它一个字都写不出来。

绑**巡检塔**,不绑 meta,两条理由:
- 这两件都是定期的活,归巡检塔(板块 `patrol`)。定规矩归 meta,查规矩归巡检塔。
- **巡检塔不被重开**(它是开塔的根,见 `tower.md`「谁来开塔:巡检塔是根」)。例程绑在会被重开的塔上,
  那个塔每换一次会话就得改绑一次 —— meta 每月都在重开名单里,0.2.x 绑在 meta 上就是这样。

另一条:**删开新会话模式的例程会把它开出来的会话一起带走**,要读试跑结果先读再删 [实测✅ 2026-09-15]。

### 0.2 绑的 ID 会变吗

平时不会:巡检塔不进每月深度重开,也永远不归档。
**万一巡检塔的会话没了**(被误归档、侧栏里找不到了),绑在旧 ID 上的例程就失效了(按门铃当场报错)[实测✅ 2026-09-25]。
这时用户在侧栏开一个新的顶层会话当巡检塔(起名「<项目>/patrol」),新巡检塔第一轮:
活表 patrol 那行换成自己的 ID → `list_triggers`(带 `include_completed: true`)找出 `persistent_session_id` = 旧 ID 的例程,
照原样(cron / prompt)在自己身上重建,再删旧的 → 报给用户改绑了哪几条。原文在 `tower.md`「谁来开塔:巡检塔是根」。
「每月深度重开」对别的塔做同样的事(`tower.md` 那一节第 7 步)。

### 0.3 从 0.2.x 升上来

0.2.x 有两条定时例程绑在 meta 上:「每日清理」「每周深度重开」。这一版换成绑在巡检塔上的「巡检塔每日」「每月深度重开」:

1. **补开巡检塔**。`node scripts/belltower-sync.mjs --add patrol --apply` 补上 patrol 板块(skill、`boards`、活表和 `CLAUDE.md` 路由表各一行);
   用户在侧栏亲手开一个顶层会话当巡检塔,起名「<项目>/patrol」,开塔口令见 `tower.md`「开塔口令」。
   它第一轮把自己的会话 ID 填进活表(`ledger-push`),给自己补 `tower`、`patrol` 两个标。
2. **旧的两条停用,别删**:`list_triggers` 找出绑在 meta 上的每日清理、每周深度重开,`update_trigger` 关掉(`enabled: false`)。
   停用的留着运行历史,要查、要再开都还在;删了就没了。
3. **在巡检塔上照本页 §1、§2 重建**。`initiation` 写 `human_request`,
   journal 记一行用户原话 + 时刻(`CLAUDE.md` 铁律6 —— 塔不许自己加例程烧钱)。
4. 两处判据跟着换了,别再照旧的做:
   - 每日清理的四条判据(只看 `list_sessions` 第一页)作废,照 `patrol.md` 第一件 —— 只看第一页会漏,只认 `worker` 标也会漏;
   - 深度重开从每周改成每月,「meta 自己除外」作废:现在只除外巡检塔,meta 跟别的塔一样重开。
5. 0.2.x 里由 meta 代开的塔,meta 一重开就在侧栏跟着折叠 [推断](塔照跑,只是侧栏里找不到)。
   每月深度重开会把够条件的塔换成巡检塔开的;不够条件、又想一起换的,第一次那轮让用户在场,问过再动。

## 1. 巡检塔每日:归档工人 · 昨晚定时 CI · 派回

**干什么**:照 `patrol.md` 跑一轮 —— 归档跑完、产出已落地的工人;报昨晚定时 CI(项目有才报);
查出来的照「归谁」派回(收件箱一行 + 门铃),拖着的回查;周一多看闸门误伤。跑完报用户一张小表。
**为什么要每天**:工人收完活就该归档(`dispatch.md` §6),但靠塔记得 = 必漏;侧边栏会越积越长,容器也不释放。
定时 CI 红了没人看,等于没跑。

**判据、步骤、早报格式都只在 `patrol.md` 里**,这里不抄第二份。0.2.x 写在本页的四条判据作废(见 §0.3)。

### 1.1 提示词(粘贴进 `prompt`)

```
【巡检塔每日】照 .claude/skills/tower-meta/references/patrol.md 做 ——
判据、步骤、早报格式都只在那份里维护,这里不抄第二份(规矩只存一份)。
几条别忘:
- 先 git fetch origin main && git merge --no-edit origin/main;台账、活表读 origin/main 的。
- 只归档不删除;不动塔;不动 RUNNING 的。
- 查出来的不自己修,照「派回的规矩」留言 + 按门铃;先 ledger-push 再按门铃。
- 跑完必须报给用户一张小表,没事也报。
```

### 1.2 怎么建

在巡检塔的窗口里建 —— 不传 `persistent_session_id`,例程就落在建它的会话自己身上:

```
create_trigger {
  name: "巡检塔每日",
  cron_expression: "CRON_TZ=<你的时区> 52 3 * * *",     # 每天凌晨,错开整点 / 半点
  prompt: <上面 1.1 全文>,
  initiation: "human_request"                            # 用户要求建的就写这个
}
```

- 从别的会话建,要传 `persistent_session_id: "<巡检塔会话ID>"`(去 `docs/session-pool.md` 塔表 patrol 那行查)。
  例程的提示词以后只能在巡检塔里改 —— 只有例程投递进去的那个会话能改(`platform-facts.md` §2)。
- cron 不带 `CRON_TZ=` 前缀按 UTC。别落在整点 / 半点(平台建议错开几分钟)。挑塔们大概率闲着的时段;
  项目有定时 CI 的,排在它的排定时刻之后一两个小时(GitHub 的定时常晚排)。
- 第一件靠标签认人:派工人打 `worker`(`dispatch.md` §4:`tags: ["worker", "Qnn", "<板块>"]`),开塔打 `["tower", <板块>]`。
  塔的标签漏了,还有「会话 ID 在活表塔表里」兜底 —— 所以塔一重开,活表就要跟着换 ID。
- 建完可以 `fire_trigger` 手动试跑一次,看报表。**只按一次**:同一个门铃按第二次会掉进新开的空会话
  [实测✅ 2026-10,装了框架的项目实测];定时例程手动按第二次会不会也这样 [未实测]。

## 2. 每月深度重开:清掉压缩摘要里攒的偏差

**干什么**:每月 1 号,对够条件的塔(**meta 也算,巡检塔除外**)做「收尾 → 归档 → 重开」。
**为什么**:上下文维护分两层 ——
**第一层**是自动压缩(`.claude/settings.json` 的 `"autoCompactWindow": 300000`,**必须是数字**,见 `platform-facts.md` §3.1),天天自己跑;
**第二层**是这个例程:压缩摘要一轮轮叠下去会慢慢走样(典型症状:塔忘了自己是塔,开始自己干成品活),每月从台账冷启动一次清掉。
装了框架的项目起初每周一轮,跑过一轮全量(五个塔约 $23)后改成每月。

**规矩只存一份**:例程提示词只写「照 `tower.md`〈每月深度重开〉那一节做」,判据和步骤只在那一节改。
下面 §2.2 把那一节的要点抄过来给你看懂,**建例程时不要把它们抄进提示词**。

### 2.1 提示词(粘贴进 `prompt`)

```
【每月深度重开】
先 git fetch origin main && git merge --no-edit origin/main,然后照
.claude/skills/tower-meta/references/tower.md「每月深度重开」一节逐步做 ——
判据、步骤、门铃原文都只在那一节维护,这里不抄第二份(规矩只存一份)。
新塔的 model:<模型名>(只写在这里,不进仓库;不写就照搬旧会话的 session_context.model)。
几条别忘:
- 巡检塔自己不重开(本例程绑在它身上,它是开塔的根);meta 照样在名单里。
- 判据有一条不中就跳过并报给用户,不硬来。
- 归档是 archive_session,绝不删除。
- 新会话的 prompt 只写 /effort max;等它 IDLE、档位是 max 了,再用门铃送开塔口令。
- 重开之后活表换新 ID(ledger-push),绑在旧会话上的例程照那一节第 7 步处理。
跑完必须报给用户一张表:谁重开了(侧边栏新会话名)、谁跳过了(为什么)、花了多少、新塔第几代。
journal 记一行,ledger-push。
```

### 2.2 `tower.md` 那一节的要点(看懂用,不进提示词)

**谁会被重开**(四条全中才动):
1. 塔表里有会话 ID 的塔,**只除外巡检塔**(它是开塔的根,不重开;要全新让用户手动 `/clear` —— 远程发 `/clear` 不生效 [实测❌ 2026-09-24])。**meta 纳入。**
2. **开局之后动过**:`updated_at` 减 `created_at` 不到 15 分钟的不动 —— 开完局就没动过,没攒偏差。
3. **开局满三周**:`created_at` 在 21 天前 —— 1 号是死日子,刚开的塔偏差还没攒起来。
4. **现在闲着**:塔不是 `RUNNING`;它派的工人(`parent_session_id` = 它)没有 `RUNNING` 的;6 小时内没动过(用户可能刚跟它聊完)。

**步骤**(八步):
1. **收尾 —— 按门铃**,让那个塔把手上的事写进台账,最后一行只写 `HANDOFF-READY`。
2. 排一个 20 分钟回查(`send_later`,打回巡检塔)。`IDLE` 且有 `HANDOFF-READY` → 往下;没有 → 这个月跳过,报给用户。
3. **归档旧会话** `archive_session` —— 不删除,转录要能回查。
4. **开新会话** `create_session`(巡检塔调):`source_url` 本仓库 + `source_revision: main`(**两个都传**,漏了新塔在侧栏落进「Other」)、
   `title` 照搬旧会话标题、`tags: ["tower", <塔名>]`(**不带 `worker`**)、`model` 用例程里写的、`prompt` **只写 `/effort max`**。
5. 新会话 `IDLE`、`effort_level` 是 `max` 了,**再按门铃送开塔口令** + 「上一任的接手须知在 journal 里本塔最新一条」
   (门铃里的 `/effort` 不当命令)。
6. **更新活表**:塔表那一行换成新会话 ID,`ledger-push`。
7. **处理绑在旧会话上的例程**:`list_triggers` 带 `include_completed: true` 全翻(不带会漏跑完的一次性回查;
   输出超上限就落盘用脚本读,条目在 `data` 下,翻页看 `has_more` / `next_cursor`),挑 `persistent_session_id` = 旧 ID 的:
   定时例程 → 照原样绑到新 ID 重建再删旧的;还没响的一次性回查 → 一样搬 [未实测];按过的门铃 → 直接删不重建(交给子代理删);
   响过的一次性回查 → 平台已停用,不管。
8. **报给用户一张表**:谁重开了、谁跳过了(为什么)、花了多少、每个新塔第几代(都该是第 1 代;到 6 单独提醒)。

**会丢的**:会话 ID(按门铃前查活表)· 用户在侧边栏跟旧塔的聊天窗口(变只读,内容都在)·
用户在侧栏单独给某个塔切的别的档位(新塔一律 `max`;`create_session` 没有 effort 参数,`max` 靠 prompt 只写 `/effort max` 设上)。
**代价**:每个塔收尾一轮(按当时上下文,约 $1.4–6.8)+ 开局一轮(约 $0.6–0.9、半分钟到一分多钟,开局就占 11–12 万上下文)[实测 2026-09,装了框架的项目]。

### 2.3 怎么建

```
create_trigger {
  name: "每月深度重开",
  cron_expression: "CRON_TZ=<你的时区> 23 4 1 * *",     # 每月 1 号凌晨 04:23,错开整点 / 半点
  prompt: <上面 2.1 全文>,
  initiation: "human_request"
}
```

- 跟 §1.2 一样在巡检塔的窗口里建。
- 选一个用户和塔大概率都闲着的时段。判据 4 会自动跳过正在忙的塔。
  1 号那天两条例程都在凌晨:每月这条比每日晚半小时(上面 03:52 / 04:23)。前一轮还没跑完,后到的排队等它跑完(门铃实测如此 [实测✅ 2026-09-25])。
- **首次跑建议人在场**:手动 `fire_trigger` 一次(只按一次,见 §1.2),对一个塔走完全程,确认新塔开局能认出自己、台账能接上,再交给 cron。
- 重开之后新塔开局 hook 靠活表里的新 ID 认身份;活表更新之前,开塔口令里写了板块,不影响。

## 3. 派工后 10 分钟回查:用户不用问「现在谁在跑」

**干什么**:塔派完工人,**同一轮里**排一个 10 分钟后的自唤醒;到点塔自己查工人和 PR,自己报给用户。
**为什么**:工人是另开的会话、另一个容器,用户在塔的窗口里**一个都看不到**(`CLAUDE.md` 铁律7)。
本地那种「能直接看到在跑」的是同一会话里的子代理,跟云工人结构上不同,改不了;能改的是「要用户来问」。

这个不是定时例程,是**一次性自唤醒**,用 `send_later`(它只能打回发起它的会话 —— 正好落在塔自己身上)[实测✅ 2026-09-10]。

### 3.1 怎么排(派工人的同一轮里)

```
send_later {
  delay_minutes: 10,
  name: "回查 Qnnn",
  initiation: "own_followup",
  message: <下面 3.2 全文,换掉占位>
}
```

### 3.2 提示词(粘贴进 `message`)

```
【回查 Qnnn】<一句话说清这单是什么>。工人会话:<派的时候 create_session 返回的 ID>,分支:claude/qnnn-<短标题>。
醒来做四件:
① get_session / list_sessions 查工人状态 —— IDLE 只说「这一轮没在出字」,不等于干完;
② list_pull_requests 查 PR 开没开、合没合 —— 不认工人自述(实测多次把「开了 PR」写成「已经合了」);
③ 没跑完就再排一个 10 分钟;跑完就按 dispatch.md §6 收活:核 diff(文件域有没有越界、台账四件有没有被碰、
   读 patch 不读描述)→ 合 PR 或提修改 → 删活表那行 → journal 一行 → 确认分支已在远端后 archive_session;
④ 把结论报给用户,一行一个工人,不要问「要不要我继续」。
```

> 这里写工人会话 ID 没问题 —— 它是塔**这一轮刚拿到的**,10 分钟后用,不是写死在仓库里的状态。

### 3.3 三条别搞错

1. **`send_later` 唤醒不了别的塔**,只打回自己。要叫醒别的塔用门铃(`create_trigger` 带 `persistent_session_id` + `fire_trigger`)。
2. **间隔照活的长短定。** 实测小单工人全程约 5–20 分钟,**首次 10 分钟**合适;没跑完再排一个,别 1 分钟一次空转烧钱。
3. **醒来先查 GitHub 再信摘要。**

### 3.4 报给用户的格式

```
Q301 dev  <一句话任务>     在跑   <它在干嘛>          —           $2.1
Q101 plan <一句话任务>     跑完   PR 开着 668 行      等 plan 收  $4.7
```

一行一个工人,别贴 JSON。报号带一句话内容(铁律5)。

## 4. 例程的维护

- **列出来**:`list_triggers`;要看某个例程当前的 prompt 和绑定,用 `get_trigger`。
- **改提示词 / cron**:`update_trigger`,不要删了重建(会丢运行历史)。
  提示词只有例程投递进去的那个会话能改 —— 前两个例程的提示词在巡检塔里改(`platform-facts.md` §2)。
  **例外**:要换绑定的会话 ID 只能重建(见 §0.2)。
- **要停就停用**(`update_trigger` 关掉),别删 —— 停用的留着运行历史。改绑时删掉旧的那条不算:它绑的会话已经没了,留着也不会再响。
- **前两个例程是用户要的才建**:建的时候 `initiation` 写 `human_request`,并在 journal 记一行用户原话 + 时刻
  (`CLAUDE.md` 铁律6 —— 塔不许自己加例程烧钱)。§3 的回查是派工配方的一部分,`initiation` 写 `own_followup`。
- 例程跑的结果要**报给用户**,不管有没有事 —— 用户看不见后台,沉默会被当成「没在跑」。
