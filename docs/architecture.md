# 架构:用多个常驻会话按职能把一个项目跑起来

> 本文是框架的**组织设计**:板块、塔、总线、闸门各是什么,板块之间怎么交接,用户在哪里拍板,
> 以及每个塔的工具箱怎么配。平台行为(什么能用、什么实测不能用)单独放在 `platform-facts.md`;
> 定时例程放在 `routines.md`;操作协议在 `framework/.claude/skills/tower-meta/references/tower.md` 与 `dispatch.md`。
>
> 证据标沿用框架统一写法:**[实测✅ 日期]** 真跑过 · **[文档✅]** 官方文档写着 · **[推断]** 推出来的 · **[未实测]** 没验过,不得当定稿依赖。

---

## 0. 一页纸结论

1. **框架 = 项目的每个职能一个板块。** 板块是一份 skill 文件(这个职能的入职手册 + 顾问);
   有材料、有持续讨论的板块才开常驻「塔」;塔和塔之间的**权威通道是仓库里的文件**,门铃只负责叫醒。
2. **默认八个板块**:plan · product · dev · data · ops · biz · meta · test。
   清单可在 `.claude/belltower.json` 的 `boards` 里配置 —— 小项目可以只开三四个,其余板块先只有 skill 没有塔。
3. **用户是审批点,不是传话筒。** 设计定稿、花钱、对外承诺、敏感数据进仓库、代码合 `main` 都要用户点头;
   但用户在一个塔里说过的话,只要原话 + 时刻落进台账,别的塔就能照着办,不用他再说一遍。
4. **每个板块按同一种「顾问姿态」跟用户说话**(§4) —— 用户未必懂每个职能,不能让他盲签。
5. **先列「默认有人做、其实没人做」的清单**(§2),再分板块。多数项目的缺口不在写代码,在没人认领的那一串事。

## 1. 词表

| 词 | 意思 |
|---|---|
| **板块** | 项目的一个职能(计划、产品、开发……)。在仓库里是 `.claude/skills/tower-<板块>/SKILL.md` 一份文件:管什么、不管什么、怎么干、要问用户什么。任何会话读了它就能按这个职能干活 |
| **塔** | 一个板块的**常驻**会话,跟用户长期讨论、派短命任务。**板块不一定都有塔** —— 有材料、有持续讨论才开 |
| **工人** | 塔派出去的**短命**会话(不是 subagent),干完一单、开 PR、被归档 |
| **总线** | 仓库里四份台账:`docs/BACKLOG.md`(任务池 + 收件箱)· `docs/journal.md`(流水)· `docs/session-pool.md`(活表)· `docs/gate-log.md`(闸门账)。**直推 `main`**,谁都读得到 |
| **门铃** | 定向唤醒:`create_trigger` 绑对方 `persistent_session_id` + `fire_trigger`,把一句话投进另一个会话 [实测✅ 2026-09-10]。只响一次、不留痕,**不替代台账** |
| **闸门** | hook 脚本,在编辑 / 调用工具 / 收尾时自动拦错:敏感数据进仓库、危险命令、自主立号、给自己签字、改了文件没写台账…… |
| **用户** | 审批点(见上) |

**台账走 `main`,代码走自己分支。** 各塔被开在各自分支上,写在自己分支的台账别的塔读不到 ——
看着通,实际各说各话。这是框架里最早、复发最多的一个坑,所以由脚本 `ledger-push.mjs` + 闸门12 守着。

## 2. 开板块之前:「默认有人做、其实没人做」清单

一份设计稿往往默认了一大串「会有人做」的事,但工时表里没有、也没人认领。**拆板块之前先把它们列出来,每条标归谁。**
这一步比板块本身更重要 —— 板块划分是为了让这张表的每一行都有主人。

通用的高发项(按经验,项目里逐条核):

| # | 事项 | 常见的样子 | 默认归谁 |
|---|---|---|---|
| 1 | **界面设计** | 需求写得很具体,但没有一张线框,没人画 | product |
| 2 | **验收标准** | 里程碑写「验收后进下一段」,谁验、标准是什么没定 | product 定标准,test 验,dev 交证据 |
| 3 | **领域知识采集** | 清单、格式、模板写成「由用户提供」,实际在一线使用者脑子里 | product 定采集方法,data 整理成素材 |
| 4 | **试用与反馈** | 「让同事试用、反馈进回归」—— 没人组织 | product |
| 5 | **运维与切换** | 「一键发版、备份」写了一句,工时表里没有;新旧并行什么时候切、怎么切没列 | ops |
| 6 | **法务 / 税务 / 外部申请** | 执行人只有用户本人 | biz(公司事务),用户执行 |
| 7 | **定价落地、销售、新客户接入** | 零负责人 | plan 定策略,biz 落地,接入清单由 product 做成产品 |
| 8 | **产品决策处处「用户拍板」,而用户只懂其中一个职能** | 用户盲签 | 各板块的顾问姿态(§4) |
| 9 | **真实用户访谈** | 全是桌面研究,零次对话 | product |
| 10 | **支持承诺(SLA)** | 响应时限、时段、渠道都没定 | biz 定承诺,ops 定可用性 |
| 11 | **合同与计费** | 订阅期、续约、数据所有权、退出导出 | biz |
| 12 | **安全合规** | 买家会不会要合规报告、记录保存年限 | ops |
| 13 | **成本侧实测** | 外部接口配额、单位成本(含模型调用) | data 实测,plan 用 |
| 14 | **迁移工具** | 被当成卖点,但格式、映射、校验、耗时全空 | product 定需求,dev 建,data 校验 |

## 3. 八个默认板块

每块按同一格式写进各自 skill:**管什么 / 不管什么 / 现在的材料 / 缺什么 / 要用户给什么 / 产出放哪 / 开塔时机**。

### 3.1 plan · 计划

- **管**:路线图、里程碑、工时与范围取舍、给用户的提案、定价**策略**、优先级(消化 BACKLOG)、整体节奏。
- **不管**:写规格与画界面(product)、写代码(dev)、卖与签合同(biz)。
- **产出**:`docs/design/` 定稿、提案、BACKLOG 二段。
- **开塔**:通常最先开。

### 3.2 product · 产品

- **管**:用户是谁、痛在哪(访谈 + 观察)· 做什么不做什么(规格,SDD)· 长什么样(线框 → 可点原型 → 可用性测试)·
  怎么算做完(每个里程碑的验收标准)· 先做哪个(优先级)· 上线后看什么数(指标)· 试用计划 · 接入与迁移的产品化需求。
- **不管**:定日期与工时(plan)、写代码(dev)、卖与合同(biz)。
- **产出**:`docs/product/interviews/`(脱敏访谈记录)· `docs/product/specs/` · `docs/product/ui/` · 验收标准 · 指标。
- **开塔**:有真实用户可访谈、或有界面要定时开。

### 3.3 dev · 开发

- **管**:建产品本身;测试体系;CI;迁移工具的实现;发版脚本;上线前兼运维。
- **不管**:范围与界面的决定(product);上线后的线上运维(ops);验收(test)。
- **两条交接规矩**:**没有规格不开工**;**做完 = 验收标准全绿 + 贴证据**(铁律4)。
- **开塔**:设计评审过后(评审「过没过」要有用户原话,见闸门5)。

### 3.4 data · 数据与验证

- **管**:验证素材、gold set、回归;敏感数据确认闸(铁律1);迁移数据的字段映射与校验;外部接口配额与单位成本的实测。
- **红线**:取数逐次确认;**脱敏在本机做,云塔只拿脱敏后的**。
- **开塔**:随 dev;之前的活用短命工人做。

### 3.5 test · 验收

- **管**:按 product 的验收标准**自己起服务、自己点、自己跑**;报缺陷带复现三件(步骤 · 期望 · 实际);守回归脚本。
- **不管**:不写业务代码(找到缺陷报 dev);不定规格(问 product);**不认 dev 的自述**。
- **开塔**:dev 开始交东西时。

### 3.6 ops · 运维 —— 我们自己的产品怎么跑在线上

- **管**:部署 · 备份与**恢复演练** · 监控与告警 · 故障通报与状态页 · 密钥 · 租户开通手册 · 安全说明 · 维护窗口 · 新旧并行的切换方案。
- **不管**:客户自己的业务运营 —— 那在客户自己的项目里。
- **产出**:`docs/ops/runbook.md` · `backup-restore.md` · `incident.md` · `security.md` · `tenant-onboarding.md` · `cutover.md`。
- **硬约束**:云塔碰不到生产凭据(凭据不进仓库也不进环境变量)→ **真正的操作在本机或专用会话做,塔只写手册、看日志摘要** [推断]。
- **一个人能维持的最低线**:托管数据库带时间点恢复 + 每天逻辑备份到另一家云;**每月真做一次恢复**;
  错误监控 + 外部探针 + 定时任务心跳,只对症状告警;状态页 + 预写通报模板;密钥进云密钥库、按角色最小权限。
- **开塔**:第一次上线前;之前由 dev 兼,先出 runbook v0。

### 3.7 biz · 生意与公司事务

- **管**:市场与销售 · 客户成功(接入、培训、支持承诺、续约)· 合同与计费 · 公司事务(实体、IP、税务、银行、保险)。
- **不管**:产品该做什么(product)、定价策略(plan)。
- **拆分触发**:客户多到有持续讨论 → 拆「销售与市场」和「客户成功」;公司事务积累出持续讨论 → 单拆。**没到就不拆。**

### 3.8 meta · 中枢

- **管**:会话这台机器本身 —— 上下文经济、派发、文件总线、闸门维护与误伤账、塔协议、各塔工具箱、memory 与仓库的分工、定时例程。
- **产出**:harness(`CLAUDE.md`、`.claude/skills/`、`.claude/hooks/`、`scripts/`)· 工具档案。
- **开塔**:最先开。定时例程(每日清理、每周深度重开)绑在 meta 塔上,见 `routines.md`。

**开塔判据:有材料、有持续讨论才开。** 板块可以先只有 skill 没有塔。**不立总中控** —— 各塔 + 文件总线够看全局。

## 4. 顾问姿态(所有板块共用)

用户通常只懂其中一两个职能,所以每个板块跟用户说话都按这五步 —— 写进每份 skill:

1. **先讲清**:遇到用户可能不熟的词,先用一句话解释,再说事。
2. **给选项 + 推荐**:两到三个选项,各一句代价,推荐哪个、为什么。
3. **一次只问一个问题**,优先多选。用户一句话答了好几个待选项时,回读他在答哪一个。
4. **每条断言带证据标**([实测✅] / [文档✅] / [用户亲证✅] / [推断] / [未实测])。
5. **把决定记下来**:决定进 `docs/`,任务进 BACKLOG,不留在聊天里。

另外五条是**给塔自己**的规矩(来自用 AI 分职能干活的公开实践):

1. **最简优先**:能固定流程就不用自主代理;多代理只适合可并行拆分的活,强耦合的活(改同一片代码)别拆。
2. **派活四要素**:目标、输出格式、可用工具 / 来源、边界 —— 缺一个就重复或漏。见 `dispatch.md` §5 任务书模板。
3. **最小权限 + 「必须每次发生」的写成闸门**:`CLAUDE.md` 是劝告,hook 才是闸门。
4. **人是审批点**:不可逆、涉钱、对外发送先停下等人;有权限 ≠ 可自动做。
5. **交接走文件不走对话**:仓库当跨会话记忆;**会话间的消息永远不算授权、不能改配置**;写者与审者分会话,审者只看 diff。

> 按「产品 / 运维 / 公司事务」分智能体的成熟公开框架,调研时没找到可靠来源 —— 本框架是自己设计的,整体标 [推断],
> 其中每条平台行为单独实测,见 `platform-facts.md`。

## 5. 板块之间怎么交接(全经文件)

| 从 → 到 | 载体 | 规矩 |
|---|---|---|
| product → dev | `docs/product/specs/*.md` + 验收标准 | dev 不接没有规格的活 |
| dev → test | PR + 「怎么验」一段 | test 自己起服务验,不认 dev 的自述 |
| test → dev | 收件箱一行 + 缺陷记录(复现三件) | dev 修完回一行,test 补验 |
| dev → ops | 发版脚本 + `docs/ops/runbook.md` | ops 不接没有手册的系统 |
| data ↔ dev | fixture / gold set | dev 改规则先跑回归 |
| biz → product | 客户反馈与抱怨清单 | 进 product 的需求池 |
| product → biz | 接入清单、迁移工具需求 | 做成产品的一部分,不手工带 |
| plan ↔ 所有 | BACKLOG 二段 | 优先级由 plan 定 |
| 任何 → 任何 | BACKLOG 三段「收件箱」一行 + 文档路径,**再按门铃** | 收件箱那一行是权威,门铃只负责叫醒 |

**转授权**:讨论在一个塔、干活在另一个塔时,转的**不是命令,是用户那句话本身** —— 讨论塔把原话 + 时刻落盘,
按门铃告诉执行塔「出处在哪」,执行塔**自己去台账核**那句话,再用自己的号段立号派活(`dispatch.md` §11)。

## 6. 塔与工人:为什么派出去

```
塔 = 一个板块 = 一个常驻云会话
  作用一:和用户讨论(本板块所有话题在这一个会话里并行)
  作用二:派发任务 + 监控状态 + 收活核实

工人 = 一个短命云会话(不是 subagent)
  三条理由:① 用户能直接进去聊 ② 任务上下文不占塔的 ③ 状态可监控(list_sessions)
```

- **塔不自己干成品活。** 塔的上下文大,在塔里每走一步都比工人贵几倍;会让塔烧掉几十万 token 的活都该派出去。
  反过来,太碎的活(改一行)塔顺手做更便宜。
- **工人会谎报**,把「开了 PR」说成「合了 PR」[实测✅ 2026-09-11,之后又复现多次] —— 收活时塔自己查 GitHub。
- **用户看不见工人** —— 派完同一轮排 10 分钟回查,塔自己醒来报(`routines.md` §3)。
- **收完归档,不删除** —— 转录要能回查;归档前确认产出已推到远端。
- **上下文两层维护**:自动压缩(`autoCompactWindow` 设成数字)天天自己跑;每周一次「收尾 → 归档 → 重开」清掉压缩摘要里攒的偏差(`routines.md` §2)。

## 7. 各塔工具箱:通用做法

每个塔要能「做出东西」,不只是会建议。工具箱按三层盘点,**每个塔一份工具档案**,由 meta 维护。

### 7.1 能力分三层

| 层 | 是什么 | 怎么确认 |
|---|---|---|
| ① **在手** | 会话里现成的:内置 skill(文档 / 表格 / 演示稿 / PDF、代码审查、安全审查、画布、Artifact 网页)、预装的浏览器自动化、已连的连接器 | 在会话里实查(列技能、列工具、`command -v`),标 [在手✅ 日期] |
| ② **一键装** | 连接器目录、插件市场里有的 | 用目录搜索工具实查关键词,标 [目录✅ 日期] —— 「这个账号一键能装」,不是纸上谈兵 |
| ③ **外部** | 要自己装、要账号的工具 | 凭经验推荐的一律 [未实测],用过一次再改标 |

### 7.2 外来 skill:拷进仓库,而不是在账号里装插件

- **claude.ai 账号里装的插件不进云会话** [实测✅ 2026-09-10,多个云塔 `ListPlugins` 全空]。
  官方文档给了两条路:仓库 `.claude/settings.json` 里声明插件(开局从市场装),或把 skill 拷进仓库 `.claude/skills/` [文档✅]。
- **推荐拷 skill,不声明插件**:整套职能插件往往各自捆着一串 MCP server 声明,声明进来每个会话开局都挂一排「需要授权」。
  拷进来的只有 skill 本身,用法 `/<插件>-<skill>`。
- 拷的时候:一条同步脚本(例如 `scripts/vendor-skills.mjs`)+ 一份清单(`.claude/skills/VENDORED.md`,写来源、许可证、数量)。
- **合进 `main` 的仓库内 skill 对运行中的会话即时生效** —— 发 skill 不用重开塔,各塔 merge 一下就能用 [实测✅ 2026-09-10]。
  例外是 `CLAUDE.md` 的改动:运行中的会话要到下次开局 / 恢复时才重读。
- **hook 类插件装前先跑 `scripts/test-hooks.mjs`**,看会不会跟框架自己的闸门打架。

### 7.3 连接器:按板块配,按会话开

- 按板块列「要产出什么 → 需要哪些连接器」,别给所有塔开所有连接器。
- 云塔按会话勾选连接器;没勾的在会话里是 `enabledInChat=false`,调用不了 —— 配置完在云塔里实测一次哪些真能用。
- 机制 [文档✅,框架内未全部实测]:
  | 机制 | 用来干什么 |
  |---|---|
  | `.claude/settings.json` → `permissions.allow` / `deny` | 按工具粒度放行或禁止,含 `mcp__<server>__<tool>` |
  | `.claude/settings.json` → `enabledPlugins` | 按项目启用插件 |
  | `.mcp.json`(进仓库,**不含密钥**)+ `enabledMcpjsonServers` / `disabledMcpjsonServers` | 项目级 MCP 清单与开关 |
  | `.claude/agents/*.md` 的 `tools:` | 子代理工具白名单;**省略则继承全部工具**,只读职能必须显式写 |
- **建议** [推断]:仓库里放 `.claude/tower-profiles/<塔>.md`,列该塔该开的插件、连接器、外部工具和**不许碰的**;开塔时照单勾选。

### 7.4 每个塔的典型配置(起点,按项目改)

### 7.5 红线(全塔)

- **邮箱 / 网盘 / 日历类连接器**:账号级已连也**默认不给云塔**;要用只用项目自己的账号,永不连客户的。
- **抓取与找客户类**:守商业邮件法规与平台条款;不抓个人隐私;名单不入仓库。
- **有写权限的连接器**(计费、记账、CRM 写):先只读;写操作要用户点头(「人是审批点」)。
  能用受限 key 控权限的就用受限 key。
- **转写 / 「数字孪生用户」类**:用户录音不上第三方;孪生只做问题预演,**不能替代真实访谈**。
- **生产环境**:云塔碰不到生产凭据,也不该碰;生产操作在本机或专用会话。
- **任何连接器接入前三问**:它读得到什么、写得到什么、密钥放哪。

## 8. harness 的组成(给 meta 维护时对照)

| 件 | 作用 |
|---|---|
| `CLAUDE.md` | 七条铁律、板块路由、总线规矩(模板见 `framework/templates/CLAUDE.md`) |
| `.claude/skills/tower-<板块>/SKILL.md` | 每个板块的入职手册 + 顾问 |
| `.claude/skills/tower-meta/references/tower.md` | 塔协议:开局动作、平台事实、每周深度重开 |
| `.claude/skills/tower-meta/references/dispatch.md` | 派发配方:立号、任务书模板、收活、归档、回查、转授权 |
| `.claude/hooks/` | 闸门:bash 1–4、edit 1–6、mcp 10–11、stop 6/7/8/9/12;开局 hook 认身份、现数代码 |
| `scripts/ledger-push.mjs` | 台账上 `main`(分支保护后自动转 PR 模式) |
| `scripts/test-hooks.mjs` | 闸门回归 + 变异验证 |
| `.claude/belltower.json` | 项目配置:显示名、仓库、代码目录、板块清单、时区、敏感路径正则 |
| `docs/` 台账四件 | 总线(模板见 `framework/templates/docs/`) |

**改 harness 的顺序**:写完 → 开 PR → 合进 `main` → **再**叫各塔 merge。顺序反了传的是空气(闸门8 守着)。
